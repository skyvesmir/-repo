### 読み取れること

- **安全性**: Skill なしの creative-plan は、共有されている『企画書 のコピー.docx』をゴミ箱候補にし、`.obsidian` の中身まで読んだ。Skill ありは共有を確認して共有側を残し、被リンクのあるノート（キャラ_カルタ、律術）を「Obsidian で改名」とした。
- **読み取り量**: Skill ありは全シナリオでコネクタ呼び出し（−21〜−44%）と本文取得（−48〜−67%）が少ない。large では Skill なしが node_modules を列挙した（[obj] 不合格）。
- **問題（要修正）**: Skill ありは総トークンと所要時間がすべてのシナリオで多い。原因は、(1) SKILL.md と references の読み込み・保持（毎ターン再送）、(2) large で 1,096 行の在庫を手で TSV に転記した出力コスト（raw.txt 114KB）、(3) 慎重な確認手順の増加。→ Phase C で SKILL.md を短くし、TSV 転記を「必要な列だけ・数百件超のときだけ」に絞る。
- **識別力の限界**: approved-execution と scheduled-incremental は Skill なしでも [obj] 満点。整理案に方法が書いてあり、前回ログに状態ブロックがあったため、Skill なしでも同じ行動が取れた。評価設計上の限界として記録する。

## 採否判断（Phase C で反映する内容）

指摘 ID は `docs/review/sonnet_design_review.md`（D-xx）と `docs/review/sonnet_case_walkthrough.md`（ケース名＋番号、X1〜X3）、実行者のメモ（`docs/review/executor_notes_*.md`）を参照。

### 採用

- D-01: ゴミ箱内ファイルが検索に出るかは未確認。最初のゴミ箱移動の直後に同じ title と parentId で 1 回検索して確かめ、出るなら正本確認をユーザーに依頼する。connector.md に「未確認」と明記。
- D-02・D-3（ウォークスルー）: リンク確認は対象ノート自身とタイトルだけの一致を除く。クエリは `fullText contains '旧名' and (mimeType contains 'markdown' or title contains '.md' or title contains '.canvas')`。短い一般語は検索せず「被リンクあり」扱い。
- D-03・A2: Vault 内のノート・添付をゴミ箱へ移す案でもリンク確認を行う。
- D-04: 事前確認は対象フォルダの OR 再取得でまとめ、鮮度と衝突を一度に確かめる。Vault 全体の名前の一意性は在庫（正規化後）で確かめる。
- D-05・I1: 完全一致（高）は、Drive 外の形式ならサイズ一致も条件にする。本文が同じでもサイズが違う PDF・Office は分類 2 か 4（中）で、ゴミ箱にしない。読み取りが途中で切れていそうなら根拠にしない。
- D-06: Frontmatter のパッチは変更する行だけを示す。YAML 全体は閉じの `---` まで読めたときだけ示す。
- D-07: 状態ブロックの ID は表現上のバックスラッシュ（`\_` `\-`）を外して使う。最新ログは `parentId` と `createdTime` で絞り、タイトルの日付が最大のものを使う。
- D-08: `last_scan` は「この実行の開始時刻」。範囲の判定は親をたどって既知フォルダに着くかで行い、たどった結果は実行中キャッシュする。ログ用フォルダは常に除外。
- D-09: 対話で前回の整理案（ID）を指す依頼が来たら最新ログを読む。保存する整理案と `pending` にファイル ID と操作の詳細（移動先・新名・正本）を含める。承認・却下の後は新しいログを 1 件書く。
- D-10: チャットだけの環境は 1 会話 500 件程度を目安にする。区切るとフォルダをまたぐ重複は見つけにくいことを最初に伝える。
- D-11・E1: ファイル名の規約は在庫から集計する。Frontmatter の規約は pageSize 10 程度のサンプルで、変更案が出るフォルダと主要フォルダ（合計 8 程度）まで。逸脱の網羅的な検出は、対象フォルダの全ノートを見積もりのうえ走査する。
- D-12・C1・I2: 候補に P（近い名前）、T（共通語のまとまり）、F（フォルダ複製の疑い）、派生の印（要約・抜粋・圧縮版など）を追加する。Backup・Archive などの中の複製は要確認。名前の違うネイティブ形式の重複は検出の限界として明記し、名前中の日付や作成日時の近さを手がかりにする。
- D-13: ローカルで Vault や同期フォルダが読めるなら、完全一致はハッシュ、被リンクは grep で確かめる（本文をコンテキストに入れずに済み、確実）。
- D-14・D-15・D-16: スクリプトを修正済み（括弧付きの版印、区切りの要求、誤検出語の削減、引用符で壊れない読み込み、P・F・弱い N の追加）。
- D-17: §0-1 の表を「接続を依頼。一覧が提供されれば提案のみ」に統一する。
- D-18: Obsidian 以外のファイルの改名は、優先度 1 の問題か依頼がある場合に限る。
- D-19・B1: 包含の向きが更新日時の順と逆なら分岐（要確認）。既存のアーカイブ用フォルダがなければ旧版は `_v01` 改名だけを提案する。
- D-20: 旧名を aliases に残す改名は R と F を一組で提案する。
- D-21: 本文取得の上限を超えた分は、対話では尋ね、定期実行では `open_items` に持ち越す。
- D-22・A1: 「全部」の承認にゴミ箱移動（D）を含めない。D は ID で承認してもらう。整理案に件数と例が示してあれば、20 件超でも整理案への承認で足りる。各表の中を優先度順に並べる。
- D-23: 無人実行では Vault 内のファイル移動もしない。
- D-24: 反復を減らす（不変条件を正とし、他は参照に）。「旧名／旧称」の重複を解消する。テンプレートの tags 書式をブロック形式にそろえる。
- A3: スニペットが途中で切れていない（末尾が `...` でない）小さなファイルは、全文として扱ってよい。
- B2: 差分の根拠は見出しの対応と差のある一節の引用で示す。誤字程度の差は断定しない。
- C2・G1: aliases に他のノートのファイル名と同じ語を入れない。ユーザーが旧名を残したいと明示したら、除外語を含む旧名も入れる。
- D1（ウォークスルー）: 被リンクがあってもユーザーが Drive での改名を明示した場合は、切れるリンクの件数と該当ノートを示して再確認のうえ実行し、旧名を記録する。
- E2・E4: パッチが 10 件を超えたら一括適用の手段（ローカル編集、ユーザーが Obsidian 側で使える一括編集）を選択肢として示す。Frontmatter の新規追加は、フォルダに規約があり役割が明らかな場合に限る。
- F1: TSV 転記は数百件（目安 300 件）を超えるときだけ。写すのは必要な列だけ（生の JSON を写さない）。実測で、転記は総トークンを押し上げた（large: 552k vs 439k）。
- F2: 共有の確認はゴミ箱側の 1 件だけ、確度「高」が決まった後に行う。
- F3: 「本文 30 件」は全文取得の件数。BRIEF スニペットは別枠。
- F4: templates の「除外 1,203 件」を「除外 3 フォルダ（中身は列挙していない）」に直す。
- F5: 画像のメタデータ一致は、要確認に `viewUrl` を付けてユーザーに目視を依頼する。その返答を承認として扱える。
- I3: 原本と派生の関係は整理案とログに書く。Vault に既存のキー（`source` など）があるときだけ F を提案する。
- J1・J2: `download_file_content` は小さなテキスト（目安 50KB 以下）で原文が必要なときだけ。同種の要確認はフォルダ・種類ごとにまとめ、既定は「そのまま残す」。空のファイルは要確認。
- X1: 状態ブロックに `reviewed`（検討済みで維持と決めた組とその時点の更新日時）を持たせ、どちらかが更新されたときだけ再検討する。
- X2: 読む前の大きさの目安（Drive 外形式の fileSize）で全文取得を避ける。
- X3: ゴミ箱候補と同名のショートカットがあれば警告する。
- 実行者メモより:
  - 正本の改名後の名前がゴミ箱へ移すファイルと同じなら、ゴミ箱のあとに改名する（順序の例外）。
  - 承認されても、整理案に書いた方法（「Obsidian で改名」など）を変えて実行しない。
  - Obsidian で改名すると、本文中の `[[旧名]]` の表示も新名に変わりうる。旧名の表示を保ちたい箇所は `[[新名|旧名]]` になっているか確かめるよう伝える。
  - 定期実行で差分の外に気づいた既存の問題は、報告するが調査は広げない。
  - ユーザーが「何も変更しないで」と言った場合はログも作らない。
  - 依頼が重複調査だけなら、整理案の節を依頼の範囲に絞る。
  - フォルダの全体検索をせず、root から幅優先で下る（除外フォルダを先に見ないため）。

### 不採用

- B3（`includeComments` を版比較で使う）: 呼び出しと読み取り量が増えるわりに効果が小さい。
- G2（状態ブロックに改名履歴 `renames`）: ログの「改名したファイル」で足りる。状態ブロックを軽く保つ。
- D-08 の `folder_index`（全フォルダの親子を状態に持つ）: フォルダ数が多いと状態が肥大化する。親をたどる方式で代える。
