# テストケースと検証結果

検証は 2 本立てで行った。

1. **仮想テストケース A〜J の机上検証**: 依頼で指定された 10 の状況について、Skill が「何を読み、何を判断し、何を変更し、何を変更せず、どこで承認を求めるか」をたどる。Phase B で Sonnet が初版をトレースし、Phase C で Opus が指摘を反映した最終版で確かめ直した。
2. **実行評価**: 模擬 Google Drive（実コネクタの挙動を再現したもの）の上で、4 つのシナリオを Skill あり・なしで実際に走らせ、呼び出しの記録と回答を採点した。

---

## 1. 仮想テストケース A〜J（最終版 SKILL.md での動き）

「指摘」は Phase B で見つかった初版の問題と、その対応先。詳細は `docs/REVIEW.md`。

### A. 同一内容・異名

- **状況**: `未整理/無題.md` と、Vault 内の `設定/世界観.md`。同じサイズ・同じ更新日時で、中身も同じ。
- **読む**: メタデータ（root から幅優先で 3〜4 回）。S 候補になるので、2 件の先頭を BRIEF の検索 1 回で取る。小さなファイルで抜粋が切れていなければ、それを全文として比べる。
- **判断**: 分類 1（完全一致）、確度「高」。正本は整理後の置き場所にある Vault 側。ゴミ箱側（無題.md）の共有を 1 回だけ確かめる。無題.md は Vault の外なので、リンク確認は要らない。
- **変更する**: 承認後、無題.md をゴミ箱へ移す。
- **変更しない**: 世界観.md。無題.md の改名（ゴミ箱の対象には他の案を出さない）。
- **承認**: D1 を ID で。「全部」には含まれない。
- **指摘**: A1「全部」とゴミ箱の関係 → SKILL §6-1。A2 Vault 内のゴミ箱候補のリンク確認 → §4-4。A3 小さなファイルは抜粋で足りる → §2 Phase 3。

### B. 最終版 / 最終版2 / 最新版に差がある

- **状況**: Google ドキュメント 3 件。「最新版」の更新日時が最も古い。「最新版」と「最終版2」は互いに相手にない内容を持つ。
- **読む**: V 候補（印を除くと同じ基本名）。3 件の先頭を BRIEF で 1 回。長い文書は全文を読まず、特徴的な一節の検索で差を探す。判断に全文が必要なら 3 件を読む（30 件の上限内）。
- **判断**: 名前ではなく内容で比べる。「最終版」は他の 2 件に含まれる旧版（分類 3）。「最新版」と「最終版2」は分岐として要確認。包含の向きが更新日時と逆なら、これも分岐として扱う。
- **変更する**: 「最終版」に `_v01` を付ける改名案（既存のアーカイブ用フォルダがなければ）。
- **変更しない**: 統合、ゴミ箱、分岐した 2 件の改名。
- **承認**: R は整理案で。どちらを正とするかは Q でユーザーが決める。
- **指摘**: B1 削除を伴う改稿で新旧を取り違える → §4-3。B2 差分の根拠の示し方 → §4-2。B3（コメントの取得）は不採用。

### C. 同じテーマで用途が違う Markdown

- **状況**: `シューニャ.md`（人物）、`キャラ_シューニャ.md`（同じ人物の旧稿）、`シューニャ設定.md`（能力設定）、`主人公シューニャ.md`（エッセイ）、`Shunya.md`（英訳）。
- **読む**: インベントリから T（「シューニャ」を含むまとまり）を作る。先頭を BRIEF で 1 回取り、役割を見る。同じ役割が疑われる 2 件だけ全文を読む。
- **判断**: 人物ノート 2 件は §4 で扱う（旧稿なら分類 3、断定できなければ要確認）。能力設定とエッセイは役割が違うので維持（分類 5）。英訳は分類 4。
- **変更する**: 名前で役割がわかりにくいものだけ改名案（被リンクがあれば Obsidian で改名）。
- **変更しない**: 役割の違うノートの統合や同名化、新しいタグの追加。`Shunya` を aliases に入れない（別ノートのファイル名と同じ語になるため）。
- **承認**: R は整理案で。人物ノート 2 件の扱いは Q。
- **指摘**: C1 同一テーマの束ね方がない → Phase 2 の T。C2 aliases と他ノートの名前の衝突 → obsidian §4。

### D. Wiki リンクされている Markdown

- **状況**: `人物/キャラ_カルタ.md`（人物ノートの規約は「名前のみ」）。`第02章.md` に `[[キャラ_カルタ]]`、`第05章.md` に `[[キャラ_カルタ|カルタ]]`、別のノートのプロパティに `"[[キャラ_カルタ]]"`。本文に画像の埋め込み。
- **読む**: 規約を BRIEF で 1 回。リンク確認の検索を 1 回（対象ノート自身は除く）。
- **判断**: 規約に合わせる改名案 R1。ヒットがあるので「検索ベース」、方法は「Obsidian で改名」。
- **変更する**: Drive では何もしない。
- **変更しない**: 埋め込みの画像、被リンク元のノートの本文。
- **承認**: R1 を整理案で。改名はユーザーが Obsidian で行う。ユーザーが Drive での改名を望んだ場合は、切れるリンクの件数と該当ノートを示して再確認する。
- **指摘**: D1 Drive で改名したい場合の扱い → obsidian §7-3。D2 MIME 固定の検索 → obsidian §7-1。D3 自己ヒットと一般語 → obsidian §7-1。

### E. Vault のルールと違う Frontmatter

- **状況**: 人物フォルダの 14 件。多数派は `type: character` と、ブロック形式の `tags`（`- 人物`）。`ペトロス.md` は `tag: 人物`、`カルタ.md` は `Tags: 人物, 主人公`、`ラナ.md` は Frontmatter なし、`アクエラ.md` は `type: キャラクター`、`シューニャ.md` は `cssclass` とプラグインのキーを持つ。
- **読む**: 人物フォルダの先頭を BRIEF で取る（pageSize 10 で 2 回）。全文は読まない。
- **判断**: F1 `tag` → `tags`（高）。F2 `Tags` → `tags` のリスト（値の「主人公」は消さない）。F3 ラナへの追加は、フォルダに規約があり役割が明らかなので提案してよい（優先度 3、中）。F4 `type: キャラクター` → `character`（中）。
- **変更する**: 変更する行だけのパッチを渡す。ローカルに Vault がある環境なら、承認後に Frontmatter だけを直接編集する。
- **変更しない**: `cssclass` とプラグインのキー（既存のキーは消さない。移行するなら件数を示して別に提案）、本文。
- **承認**: F は整理案で。
- **指摘**: E1 サンプルと網羅的な検出の区別 → obsidian §2。E2 パッチの手作業が重い → obsidian §8。E3 抜粋ではインデント幅が分からない → obsidian §8。E4 Frontmatter のないノートへの追加 → obsidian §4。

### F. 1,000 件以上（コードのフォルダと Vault が混在）

- **状況**: マイドライブに約 1,500 件。`tool-app/` に `package.json` と `node_modules`（約 700 件）、Vault に約 385 件、写真 150 件、資料 100 件など。
- **読む**: root から幅優先で下り、`tool-app` の直下で `package.json` を見つけたら、それ以上は下らない。`.obsidian` も列挙しない。一覧は抜粋を切って 30 件ずつ、複数フォルダを OR でまとめる。300 件を超えるので、書き出せる環境ではスクリプトで候補を出す。本文は 30 件まで。
- **判断**: 写真の S 一致は本文を比べられないので確度「中」。`viewUrl` を付けた要確認にする。
- **変更する**: 整理案まで。実行は承認後。
- **変更しない**: 除外フォルダの中身。
- **承認**: 20 件を超える改名・移動は件数と例を示して。ゴミ箱は ID で。
- **指摘**: F1 TSV への転記がトークンを押し上げる → Phase 2（300 件超のときだけ、必要な列だけ）。F2 共有確認の回数 → §4-4。F3 30 件の数え方 → §3。F4 テンプレートの矛盾 → templates。F5 画像の目視 → §4-5。
- **実行評価**: large-dup-survey（下の 2 章）。

### G. 旧ファイル名が別名として必要

- **状況**: `設定/魔法体系_最終版2.md`。`第03章.md` から `[[魔法体系_最終版2]]`。ユーザーは「魔法体系に改名したい。ただ旧名でも検索したい」と言っている。
- **読む**: 規約を BRIEF で 1 回、リンク確認の検索を 1 回。
- **判断**: R1（魔法体系.md へ、被リンクがあるので Obsidian で改名）と F1（aliases に旧名）を一組で提案する。ユーザーが明示しているので、「最終版2」を含む旧名でも aliases に入れる。aliases では既存のリンクは直らないことを伝える。
- **変更しない**: 第03章の本文（リンクの書き換えは Obsidian の自動更新に任せる）。
- **承認**: R1 と F1 を一組で。
- **指摘**: G1 除外規則とユーザーの明示の衝突 → obsidian §4。G2（改名履歴を状態に持つ）は不採用。

### H. 同名ファイルが別フォルダにある

- **状況**: Vault の `人物/カルタ.md`（現行）と `旧設定/カルタ.md`（旧稿）。Vault 外の `資料/2025/議事録.docx` と `資料/2026/議事録.docx`（年度違い）。同じフォルダに `請求書.pdf` が 2 つ。
- **判断**: カルタ 2 件は分類 3。Vault 内で名前が重なるので、旧稿に改名案（Obsidian で改名）。議事録は分類 5 で両方残す。請求書は S かつ本文一致なら分類 1 で、ゴミ箱の案。
- **変更しない**: 議事録 2 件、現行のカルタ.md。
- **承認**: R は整理案で、D は ID で。
- **指摘**: H1 N の定義が同じフォルダ内の同名を落とす → Phase 2。

### I. 原本と派生資料

- **状況**: `市場調査レポート.pdf`（3.2MB）と `市場調査レポート_圧縮版.pdf`（0.8MB、本文は同じ）。Vault に `研究/市場調査_要約.md`（「出典: 市場調査レポート.pdf」）。
- **読む**: 派生の印「圧縮版」で V 候補。PDF は 1MB を超えるので全文を読まず、先頭と一節の検索で比べる（確度は「中」まで）。要約.md は先頭で出典がわかる。
- **判断**: 圧縮版はサイズが違うので分類 1 にせず分類 4。要約も分類 4。
- **変更する**: なし。関係を整理案とログに書く。Vault に `source` などの既存キーがあれば F を提案する。
- **変更しない**: 3 件すべて。
- **指摘**: I1 サイズ違いを完全一致にしうる → §4-1。I2 派生の発見手段 → 派生の印。I3 関係の記録先 → §4-1、obsidian §4。

### J. 判断できないファイル

- **状況**: 画像だけの PDF、`data.bin`、0 バイトの `メモ.txt`、空の Google ドキュメント「新規ドキュメント」、HEIC 画像、MIME が PDF の `report.docx`。
- **読む**: メタデータと、フォルダの先頭の抜粋 1 回。`download_file_content` は使わない。
- **判断**: 分類 6 と X（異常）で要確認。同じ種類はまとめて 1 行にし、既定は「そのまま残す」。「無題」「新規」だけを理由に改名しない。
- **変更する**: なし。
- **承認**: 要確認に「判断に必要な情報」を書いて尋ねる。
- **指摘**: J1 `download_file_content` の誤用 → §3。J2 要確認のまとめ方 → §8。J3 「そのまま残す」の記録 → 状態ブロックの `reviewed`。
