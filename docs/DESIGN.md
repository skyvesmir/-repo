# 設計説明と安全上の注意

Drive Organizer & Obsidian Optimizer の設計の考え方、ファイル構成、利用者向けの安全上の注意、既知の限界をまとめる。

## 1. この Skill がすること

Google Drive の数百〜数千件のファイルを、「メタデータ → 候補 → 必要な本文だけ」の順に調べ、重複・命名・置き場所の整理案を出す。承認された項目だけを実行する。Obsidian の Markdown は、既存の Vault の規約に合わせてファイル名と Frontmatter（title, aliases, tags, date, type）を整える。

## 2. 設計の柱

### 2-1. 読む量を段階的に絞る

全ファイルの本文は読まない。安い情報から順に使い、判断がついたらそこで止める。

1. メタデータ（名前、MIME、サイズ、日時、親フォルダ）で全体を把握し、インベントリを作る
2. インベントリだけで候補を抽出する（同じサイズと更新日時、同じ名前、版の印、近い名前など 11 種類）
3. 候補だけ、先頭の抜粋（約 1000 文字）を検索 1 回でまとめて取る
4. 特徴的な一節で全文検索し、派生や転記を探す
5. それでも決まらず、ゴミ箱への移動などがその判断に依存するときだけ、全文を読む（1 回の実行で 30 件程度まで）

読んだファイルは要約メモに残し、二度読まない。300 件を超えるときは、候補の抽出をスクリプト（`scripts/find_candidates.py`）に任せる。検索結果を表に書き写す作業がいちばんの負担になるので、表には必要な列だけを書き、ID は先頭 10 文字程度、MIME は `pdf`・`gdoc` などの短い書き方でよいことにした。

### 2-2. コネクタの実測に合わせる

実際の Google Drive コネクタを読み取り専用で調べ、分かった制約を前提にした（`references/drive-connector.md`）。

- 本文を書き換えるツールがない → Frontmatter はパッチとして渡すか、ローカルに Vault がある環境でだけ直接編集する。「作り直して古い方をゴミ箱へ」という置き換えは禁止した（ファイル ID・版の履歴・共有が失われるため）。
- 完全削除のツールがない → 不要なものはゴミ箱へ移すだけ。
- pageSize は 30 まで実用、既定の抜粋は約 5000 文字 → 一覧は抜粋を切って 30 件ずつ取る。
- 検索は記号を無視する → 「(1)」などの印は検索ではなく、取得済みの一覧で判定する。

### 2-3. 断定しない

- 重複を 6 つに分類する（完全一致／ほぼ同一／別バージョン／原本と派生／関連するが別物／判断不能）。名前やサイズだけでは確定せず、確定には本文の比較を要する。
- 確度（高・中・低・要確認）で行動を制限する。ゴミ箱の案は「高」だけ、改名・移動は「中」以上。
- 「最終版2」「最新版」などの名前ではなく、内容で新旧を判断する。互いに相手にない内容があれば分岐として、ユーザーに判断を委ねる。
- 被リンクの確認は「確認済み／検索ベース／未確認」のどれかを必ず明示し、確かめていないものを「安全」と言わない。

### 2-4. 壊さない

- 承認の要否を操作ごとに決めた。ゴミ箱への移動は ID を挙げた承認が必要で、「全部」には含めない。
- 実行の直前に対象を取り直し、整理案の時点から変わっていないか、移動先に同名がないかを確かめる。
- 順序は「フォルダ作成 → 移動 → 改名 → ゴミ箱」。途中で止まっても何も失われない。
- 承認された方法を差し替えない（「Obsidian で改名」とした項目を Drive で改名しない）。

### 2-5. Obsidian は「規約が先、役割で判断」

- 変更案を作る前に、Vault の規約（命名、キー名、タグの語彙、type の値）を少数のサンプルから把握し、それに合わせる。規約そのものは勝手に変えない。
- 同じ役割のノートは統一し、役割が違うノートは維持する（「シューニャ」と「シューニャ設定」は人物と能力設定で役割が違う、など）。
- Drive 側での改名は `[[リンク]]` を切る。aliases に旧名を入れても既存のリンクは直らない。被リンクがありうるノートの改名は「Obsidian で改名」を方法にする。
- 日記ノート、テンプレート、`.excalidraw.md`、自動命名の添付は改名しない。tags は既存の語彙を優先し、1 ノート 1〜3 個。date にファイルの日時を流用しない。

### 2-6. 定期実行は「差分・状態・無人では消さない」

- 前回のログの先頭にある状態ブロックから再開し、前回以降の新規・変更ファイルと、未解決の要確認だけを調べる。
- 却下された提案と、検討して維持と決めた組は繰り返さない。
- 前回の状態が読めなければ、そう書く。存在しない履歴を推測しない。
- 無人の実行では、ゴミ箱への移動、Vault 内の改名・移動、Frontmatter の適用をしない。

### 2-7. 必要な説明だけを読む

評価で、Skill の説明を読むこと自体がトークンを押し上げると分かった。そこで SKILL.md には常に必要な規則だけを置き、詳細は場面ごとの参照ファイルに分けた。

| ファイル | 読む場面 |
|---|---|
| `SKILL.md` | 常に |
| `references/drive-connector.md` | 常に（最初に） |
| `references/obsidian.md` | Obsidian のノートについて、改名・移動・ゴミ箱・Frontmatter の案を作る、または実行するとき |
| `references/templates.md` | 整理案・ログを書くとき |
| `references/scheduled.md` | 定期実行のとき。または前回の整理案の ID を指され、その内容が会話にないとき |
| `scripts/find_candidates.py` | インベントリが 300 件を超え、コードを実行できるとき |

## 3. ファイル構成

```text
drive-organizer-obsidian-optimizer/
├── SKILL.md                     本体（手順・判断基準・承認規則）
├── references/
│   ├── drive-connector.md       コネクタの実測メモとクエリ集
│   ├── obsidian.md              Obsidian の命名・Frontmatter・リンクの詳細
│   ├── scheduled.md             定期実行と、前回の続きの扱い
│   └── templates.md             整理案・作業ログ・状態ブロックの形式
├── scripts/
│   └── find_candidates.py       インベントリ TSV から候補を抽出する
└── evals/                       評価用（配布パッケージには含まれない）
    ├── evals.json               4 つのテストシナリオと採点項目
    └── harness/                 模擬 Drive、テストデータ、機械採点、盲検採点と集計の補助、指示文の雛形
```

## 4. 利用者向けの安全上の注意

1. **ゴミ箱の中身は 30 日ほどで完全に消えます**（Google Drive の仕様）。ゴミ箱へ移した後は、早めに作業ログを見て、必要なものがないか確かめてください。復元は Drive の画面から行います（コネクタには復元の手段がありません）。
2. **Obsidian のノートの改名は、できるだけ Obsidian の中で**行ってください。設定の「内部リンクを自動更新」を有効にしておくと、リンクも書き換わります。Drive 側で改名すると `[[リンク]]` は切れます。
3. **リンクの確認は検索に基づくもので、完全ではありません**。「検索ベース」と書かれた改名の後は、Obsidian でリンク切れがないか確かめてください。
4. **Frontmatter の変更は、パッチとして渡されます**。コネクタでは本文を書き換えられないため、適用はユーザー（または Vault をローカルで扱える環境の Claude）が行います。
5. **Google Drive for desktop などで Vault を同期している場合**、Drive 側の変更はローカルの Vault にも反映されます。大きな整理の前には Vault のバックアップを取ることを勧めます。
6. **共有されているファイルは、ゴミ箱の案から外すか正本にします**。ただし、共有相手がどう使っているかまでは Skill では分かりません。
7. **他人がオーナーのファイルとショートカットは変更しません**（報告だけ）。
8. **定期実行は提案だけ**です。事前に許可しても、ゴミ箱への移動や Vault 内の改名は実行しません。

## 5. 既知の限界

- **書き込み系のツールは、実際の Drive では試していません**。利用者のデータを変えないため、実コネクタは読み取り（検索・メタデータ・本文取得）だけで調べました。改名・移動・ゴミ箱・作成の挙動は、ツールの説明と模擬環境に基づいています。
- **ゴミ箱内のファイルが検索に出るかは未確認です**。最初のゴミ箱移動の直後に確かめる手順を入れてあります。
- **名前の違う Google ドキュメントどうしの重複は、ほとんど見つけられません**。ネイティブ形式はサイズが本文量と対応しないため、メタデータで候補にできません。見つかるのは、名前の日付などの手がかりが重なる組だけです（評価では「議事録_0612」と「2025-06-12_定例」の組を、この方法で見つけました）。
- **本文の比較は Claude が読んで判断します**。ローカルに Vault がある環境を除き、ハッシュでの機械的な照合はできません。そのため、ゴミ箱の案には本文の比較と確度「高」を必須にしています。
- **被リンクの確認は Markdown と `.canvas` だけ**を検索します。ブックマークなど、その他の参照元は見ていません。
- **定期実行の差分は、自分がオーナーのファイルだけ**が対象です。共有フォルダの中で他人が作ったファイルの変化は拾えません（報告の制約に書きます）。
- **トークンと時間は、Skill なしより増えます**。実行評価では、Drive の呼び出しが 41%、本文の取得が 68% 減った一方、トークンは平均 29%、時間は平均 89% 増えました。Skill の説明を読む固定の量と、書き込み前の確認（共有・被リンク・事前確認）の分です。1〜2 件の改名のような小さな依頼では、この固定の量が目立ちます。
- **評価は模擬 Drive 上で、各シナリオ 1 回ずつ**です。実行ごとのばらつきは測っていません。Skill あり（初版・最終版）は 43 項目すべてに合格し、Skill なしは 33 項目でした。4 シナリオのうち 2 つは、Skill なしでもほぼ満点で差が出にくく、採点担当は項目の弱さも指摘しています（詳細は `docs/TEST_CASES.md` §2）。
- **最終版の再テストの後に加えた文言の明確化とスクリプトの改良は、Skill 全体では再テストしていません**。判断の方針は変えておらず、スクリプトは単体で検証しました（`docs/REVIEW.md`）。
