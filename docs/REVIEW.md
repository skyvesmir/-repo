# Sonnet の指摘と Opus の採否（Phase B → Phase C）

Phase B で Sonnet が行った検証の指摘と、Phase C で Opus がどう扱ったかの一覧。指摘の原文は `docs/review/` にある。

- `sonnet_design_review.md`: 設計レビュー（D-01〜D-24）
- `sonnet_case_walkthrough.md`: 仮想テストケース A〜J の机上トレース（ケース名＋番号、追加の X1〜X3）
- `executor_notes_*.md`: 評価の実行担当（Sonnet）が残したメモ

採否の方針: 誤操作・誤判定につながるものと、要件に対する欠落は採用する。呼び出しや読み取りを増やすわりに効果が小さいもの、状態を肥大化させるものは採用しない。Sonnet の提案文はそのまま使わず、既存の規則との重複や矛盾を解いてから反映した。

## 2. 採用しなかったもの

| 指摘 | 要旨 | 理由 |
|---|---|---|
| B3 | 版の比較で `includeComments` を使う | 呼び出しと読み取り量が増えるわりに、判断が変わる場面が少ない |
| G2 | 状態ブロックに改名の履歴（`renames`）を持つ | 作業ログの「改名したファイル」で足りる。状態ブロックを軽く保つ |
| D-08 の一部 | 全フォルダの親子関係（`folder_index`）を状態に持つ | フォルダが多いと状態が肥大化する。親をたどって判定し、実行中だけ覚える方式で代える |
| D-01 の一部 | 状態ブロックに `trashed_ids` を持ち、在庫から除く | ゴミ箱内のファイルが検索に出るかをまず確かめる（`trashed_in_search`）。出ると分かってから考えればよい |
| C（ケース C）の一部 | T の束ね方を `title contains` の検索で行う | インベントリ（取得済み）から数えれば追加の呼び出しが要らない |
| iteration-3・大規模 | サイズの大きい PDF・Office で抜粋が極端に短いとき、BRIEF を全文とみなす基準を決める | §4-2（サイズに比べて極端に短い読み取りは根拠にしない）で足りる。テストデータの PDF は中身が短すぎる人工的なもので、実データでは起きにくい |
| iteration-3・創作 | Google ドキュメントのコメントや版履歴も比べる | B3 と同じ理由 |
| iteration-3・大規模 | 検索結果の並び順（更新日時の降順に見える）を説明に書く | 模擬環境の挙動で、実コネクタでは確かめていない |
