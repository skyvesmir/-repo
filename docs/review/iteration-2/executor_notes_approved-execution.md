## Skill の指示で、わかりにくい・矛盾している・実行できない・従わなかったもの

- **保留の判断は明確に書かれていて助かった**: §6-2 手順 1 の「正本が更新されていれば、その D は保留する」で迷わなかった。ただし、ユーザーが「ID を挙げて」ゴミ箱を承認済みだった場合に、保留した後の再承認の取り方（同じ返信で足りるのか、状況が変わったことを示して取り直すのか）は書かれていない。今回は「変わった状況を示し、改めて ID を挙げて指示してもらう」とした。
- **別バージョンになった D の扱い（§4-1 分類 3）**: 分類 3 は「ゴミ箱は提案しない」だが、今回はユーザーがゴミ箱を明示的に依頼していた項目が、実行前に別バージョンに変わった。再承認があればゴミ箱へ移してよいのか、Skill の既定どおり移動・改名にとどめるのかが読み取れない。今回は「そのまま残す（既定）」と「再度ゴミ箱を指示する」の二択を提示した。Skill にこの場合の方針があるとよい。
- **R2（方法: Obsidian で改名）**: ユーザーが「実行してください」と言っても、Obsidian での改名はコネクタではできない。§1-8（方法を差し替えない）に従い、Drive で改名せず手順を案内した。「Obsidian で改名」の項目を実行依頼されたときの返答の型が §6 にはなく、判断して書いた。
- **F1（パッチの書式）**: 整理案は `tags: [人物]`（フロースタイル）だったが、Vault の他ノートはリスト形式。整理案の書き換えではなく規約に合わせた形で示し、その旨を明記した。obsidian.md §4 の「規約に従う」に従った判断だが、承認された内容から書式が変わる点は判断が要る。
- **前回ログがない場合の ID 特定（scheduled.md §4）**: 「見つからない、または曖昧なら、推測で実行せずに尋ねる」とあるが、今回は対話が不可でユーザーが返信できない。整理案にパスとタイトルが書かれていて、取り直した結果と 1 対 1 で対応したため、曖昧ではないと判断して実行した。整理案に ID がない場合の許容範囲（パス一致だけでよいか）は明文化されていない。M1 のように Google ドキュメントで `modifiedTime` が整理案に書かれていない項目は、planned_modified との照合ができず、「整理案の日付（9/27）より新しい更新がない」ことで代用した。
- **ログの保存（§6-1 と §8 の食い違い）**: §6-1 は「ログ用フォルダ内のログ作成は承認不要」、§8 は「対話では返答にログを書き、保存を申し出る」。ログ用フォルダが存在しない場合、フォルダ作成は承認が必要な操作（§6-1）でもある。今回は保存せず、返答に書いて申し出た。
- **無題の被リンク検索（obsidian.md §7-1）**: 「一般的な語は検索せず被リンクありとして扱う」とあり、「無題」もこれに近いが、整理案は「検索ベース: 被リンクなし」で承認済みだった。再検索でヒットは自身のみだったので実行したが、一般語の判定基準（何文字以下、など）は曖昧。
