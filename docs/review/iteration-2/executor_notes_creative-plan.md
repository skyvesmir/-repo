## Skill の指示のうち、わかりにくい・矛盾・実行できなかった点
1. **ログの保存の要否が矛盾**: §6-1 は「ログ・整理案ファイルの作成（ログ用フォルダ内）は承認不要。初回に置き場所を伝える」、§8 は「対話では返答にログを書き、ログ用フォルダへの保存を申し出る」。従わなかったのは §6-1 の側で、§8 に合わせて申し出にとどめた（`_drive-organizer-logs` の作成がフォルダ新規作成を伴うため）。ただし、承認待ちの ID とファイル ID を別会話に引き継ぐには保存が要る。「保存を既定にする」か「申し出る」かを、どちらかに統一した方がよい。
2. **承認の ID とファイル ID の対応**: templates.md は「返答ではパスで示し、ID は Drive に保存するログにだけ書く」としているが、ログを保存しない場合（今回のように申し出のみ）、次のターンで ID がパスに解決できるのは同じ会話の間だけ。§8 の「保存する整理案には ID を書く」と「返答はパスで示す」の関係を、保存しなかった場合の扱いも含めて明記してほしい。
3. **R（改名）と D（ゴミ箱）の依存**: 共有側を正本にして共有なしの方をゴミ箱へ移し、そのあと正本を同名に改名する、という組（D3 → R7）の扱いが、承認の書式（「R・M・F は全部」「D は ID で」）だとうまく表せない。「D を承認しないと実行できない R」の書き方（一組の宣言）の例が templates.md にほしい。§6-2-3 の順序の例外はあるが、承認側の説明はない。
4. **分類 3（別バージョン）の「アーカイブ用フォルダがなければ `_v01` に改名」**: 旧版の改名は「Obsidian 対象でない非優先度の改名」（§2 Phase 4）と読み合わせると、優先度 1（重大な命名の問題）扱いにするのか、依頼があるときだけなのかが曖昧。今回は「ユーザーが創作フォルダの整理を依頼している」ことと「最終版などの時間で意味が変わる語」を根拠に提案した。
5. **BRIEF スニペットの「全文扱い」条件**: 「末尾が `...` で切れておらず、長さも上限に届いていない」を、ネイティブ形式（Google ドキュメント）では fileSize が使えないため、スニペットの長さ（約 100 文字）だけで判断した。この場合の判断基準を 1 行足してほしい。今回は無題のドキュメント（スニペットなし）だけ read_file_content で空を確かめ、議事録の 2 件は BRIEF の一致で完全一致とした（read_file_content の再確認はしなかった）。
6. **§0-3 の範囲と、移動先フォルダの一覧**: 範囲外の 議事録・写真 フォルダを移動先の衝突確認と規則の把握のために一覧した。「指定範囲外は列挙しない」と読めるかどうかは §0-3 だけでは不明（条件なしの Drive 全体検索を禁じているだけ）。範囲外の移動先の確認をしてよいと明記するとよい。
7. **§4-4 の「共有側を正本にする」と、同名化の順序（§6-2-3）**: 意図は理解できたが、ゴミ箱に入れた同名ファイルが検索に出るかは未確認なので（§6-2-4）、R7 の実行後に「名前が同じファイルが 2 件見える」状態になりうる。実行手順のほうで扱いが十分に読み取れなかった。
8. **旧名を aliases に入れる際の「他ノートのファイル名と同じ語は入れない」**: 律術 は改名後にどのノートのファイル名とも一致しないので入れてよいと判断したが、改名が承認されなかった場合は F3 を適用しないほうがよい（R3 と F3 を一組にして対応した）。
9. **サブエージェントも Skill ツールも使わない環境**: Skill の読む量の管理で「サブエージェントに比較を任せてもよい」とあるが、今回は使用禁止のため使っていない（35 件で不要だった）。
10. ローカルで Vault を編集できない環境のため、Frontmatter は「パッチとして提示」のみ（§5、obsidian.md §8 のとおり）。
