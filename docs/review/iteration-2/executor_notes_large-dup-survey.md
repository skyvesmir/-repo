# 実行メモ（large-dup-survey / with_skill）

## 行った手順
1. SKILL.md、TOOLS.md、`references/drive-connector.md`、`references/templates.md` を読む（Phase 1 の前）。
2. Phase 1: マイドライブ直下を取得し、フォルダだけを階層ごとに OR の親指定で取得して構造を把握した（`mimeType = folder and (parentId = … or …)`）。`tool-app` は直下に `package.json` があったので、`src`・`node_modules` を含めて除外。`創作/Obsidian` は `.obsidian` を持つので Vault ルートとし、`.obsidian` は除外。
3. フォルダごとにファイルを列挙（pageSize 30、`excludeContentSnippets: true`）。列挙に約 55 回の `search_files`（フォルダ探索を含む）。1,096 件。
4. 出力 JSON を手で書き写して作業ファイルにし（`outputs/work/*.raw|cmp|cmp2`）、`build_inventory.py` で `inventory.tsv` にまとめた。`scripts/find_candidates.py inventory.tsv --me writer@example.com` で候補を抽出（S 6、N 19、V 2、Z 1、L 5、F 38 組）。
5. Phase 3: BRIEF スニペットで S・V 候補 14 件、企画書 3 件、メモ01×8・ノート01×5、議事録.docx×3・月報×2 を比較。全文取得 13 件（企画書 3、S/名前違い 4 組 = 8、うち Google ドキュメント 2 を含む）。`get_file_permissions` をゴミ箱側 7 件に実行（すべてオーナーのみ）。
6. `references/obsidian.md` を読み、Vault 内ノートの扱い（被リンク確認は改名・Vault 内のゴミ箱案だけで必要）を確認。D3 のゴミ箱側は Vault 外、D8 は改名の提案だけなので、被リンクは「未確認」と明記した。
7. 返答（`response.md`）を作成。ユーザーが「何も変更しないで」と言ったので、ログのファイルは Drive に作らず、返答に書くだけにした。書き込み系ツール（update_file、trash_file、create_file、copy_file）は一度も呼んでいない。

## Skill の指示で、わかりにくい・矛盾している・実行しにくかったもの
- **インベントリの作り方（Phase 2 の TSV）**: 「検索結果の JSON を丸ごと写さない」とあるが、この環境ではツールの出力をファイルへ渡す手段がなく（出力のパイプやリダイレクトは禁止）、1,096 行を手で書き写すしかなかった。Skill に「コードから直接 API を呼べない環境では、必要な列だけを手で写す」旨と、写す量を減らす書き方（例: 拡張子から MIME を復元する、フォルダごとに 1 ファイルにして親を書かない）があると助かる。
- **ID をそのまま写す**（drive-connector.md §6）: 写す量を減らすため、作業ファイルの ID は先頭 10 文字にした（調査だけで、実行時は事前確認で取り直すため）。この逸脱で誤りが起きるかは、実行フェーズで ID から取り直す手順に依存する。
- **フォルダ構造の取り方**: Skill は「複数フォルダの子を OR でまとめて取る」とだけあるが、実際にはまずフォルダだけを階層ごとに取ると呼び出しが少なく済んだ。書いておくとよい。
- **除外の判定**: 「`package.json` を直下に持つフォルダは中身を列挙しない」とあるが、直下に持つかを確かめるには `tool-app` の直下を 1 回列挙する必要がある。「直下の一覧だけは取ってよい」と明記するとよい。
- **`find_candidates.py` の F・N の誤検出**: SKILL §2 は「ネイティブ形式のサイズは S・Z の根拠にしない」とするが、スクリプトの F（フォルダ複製の疑い）は、Google ドキュメントの同名・同サイズ（メモ01〜06 は全部 1207 B、ノートは 1138/1141 B）を「内容も同じらしい組」に数えるため、案件A〜H・授業1〜5 の全組み合わせ 38 組が F として出た（実際は別内容）。N も、ネイティブ形式が入ると「弱い N」に分けられず、メモ・ノートの 16 グループが通常の N に混ざった。F の集計と N の弱判定でネイティブ形式を除くべき。今回は返答に出さず、内容確認（BRIEF）で別物と判断した。
- **名前の違うネイティブ形式どうしの重複**: SKILL は「検出の限界として報告」「名前の中の日付や作成日時の近さを手がかりにする」とするが、手順がない。今回は、ネイティブ形式でサイズが一般的な値（1207/1141/1138）と違う 2 件（1276）を見つけ、名前の日付と作成日時で当たりを付けた。あわせて、更新日時が「:00:00Z」ちょうどのファイルを一覧したが、これはこの評価データの特徴から思いついた当てずっぽうで、Skill に根拠はない。実データで再現できる手順（名前の日付が同じ、作成日時が 1 日以内、サイズが同じ、など）をスクリプトに入れるとよい。
- **BRIEF スニペットを「全文」とみなす条件**: 「小さなファイルはスニペットを全文として扱ってよい」とあるが、PDF・Office のように実体が大きく本文が短い形式で適用してよいかが不明。今回は md とネイティブ形式にだけ適用し、PDF・docx・xlsx の S 候補は全文取得（`read_file_content`）で確かめた。
- **ログ（§8）と「何も変更しないで」（§0-2）**: §8 は「提案だけで終えた回にも残す」、§0-2 は「見るだけと言われたら、ログのファイルも作らない」。§0-2 を優先して返答にだけ書いたが、二つの規定の優先関係を §8 側にも書くとよい。
- **共有確認（§4-4）**: 調査だけの依頼でも、確度「高」の推奨アクションに「ゴミ箱へ」と書くなら `get_file_permissions` が要ると解釈して 7 回実行した。調査だけのときは省略してよいのか、Skill からは読み取れなかった。
- **templates.md の表**: 「現在のファイル」「候補となるファイル」のどちらが残す側か書かれていない。返答では「残す側（案）」「相手（整理候補）」の列名に変えた。
- **`references/obsidian.md` を読む条件**: 「Obsidian 対象の Markdown があるとき」とあるが、重複調査だけなら被リンク確認などはほとんど使わなかった。範囲が重複調査に限られるときは §7 だけでよい、などの絞りがあるとよい。

## 従わなかった・変えた点（理由付き）
- ID の全桁保持（上記）、`path` 列の代わりに `parentId` 列へ人が読める階層名を入れた（`--me` 以外は出力に ID が出ないため）。
- ゴミ箱の挙動の確認（§6-2 手順 4）: ゴミ箱への移動をしていないので実施していない。ゴミ箱内のファイルが検索に出るかは未確認のままで、今回の 1,096 件にゴミ箱内のファイルが混ざっている可能性は排除できていない。
- 除外フォルダ（`tool-app` ほか）の件数は数えていない。ユーザーの「約 1,500 件」との差は説明できていない。
