# 設計レビュー（Phase B・検証担当）

対象: `drive-organizer-obsidian-optimizer`（SKILL.md / references/drive-connector.md / references/templates.md / scripts/find_candidates.py）
基準: `docs/REQUIREMENTS.md` と `evals/harness/TOOLS.md`（実コネクタのツール面）

## 0. 総評と検証方法

- 全体として、実コネクタで実現できる範囲に収まっており、TOOLS.md に存在しないツール・引数・クエリ項目への依存は見つからなかった（`search_files` の項目、`update_file` の title/parentId 限定、`trash_file` のみ、`create_file` の `disableConversionToGoogleType` などはすべて一致）。
- 安全面の骨格（完全削除なし、本文書き換えなし、確度「高」のみゴミ箱、定期実行では無人の破壊的操作を禁止）は堅い。
- 問題は「安全の骨格の外側」に集中している。具体的には、(1) リンク確認とゴミ箱移動の穴、(2) 定期実行の状態受け渡し、(3) 大規模時の呼び出し・コンテキスト設計、(4) 候補抽出の網羅性とスクリプトの品質。
- 「重大」に固定した指摘はない。ただし D-01 はコネクタの挙動次第で重大になる（誤ってゴミ箱にある方を残す案が出うる）。
- スクリプトは `/tmp/vtest/` に TSV を作って実行し、挙動を確かめた（D-14〜D-16 の根拠）。スキルのファイルは編集していない。

## 2. 指摘の詳細

### D-01（中・条件付きで重大）ゴミ箱内ファイルの扱いが未確認のまま

- 場所: drive-connector.md §1「返らない: ゴミ箱に入っているかどうか」、§2「ゴミ箱内のファイルを除く条件はクエリに書けない」。SKILL §4-3（正本の選び方）、§6-2-1（正本の存在確認）。
- 問題: 作者自身が「除けない・判別できない」と書いているのに、対処が SKILL にない。コネクタが検索結果にゴミ箱内ファイルを返す場合、次が起きる。
  - 過去にユーザーがゴミ箱へ入れたコピーが「重複相手」として在庫に入る。
  - 自分が前回ゴミ箱へ移したファイルが、次回の在庫や差分に再登場する。
  - §4-3 の優先順位③「名前が整っている」④「作成日時が古い」で、ゴミ箱内のコピーが正本に選ばれる。
- 失敗シナリオ: S グループ {A（通常）, B（ゴミ箱内）}。B が正本に選ばれ、A のゴミ箱移動が提案され、承認される。両方がゴミ箱に入り、30 日後に両方消える。§6-2-1 の「正本の存在・未変更の確認」は `get_file_metadata` に trashed 情報がないため検出できない。
- 最小の修正:
  1. 最初にゴミ箱へ移したファイルの直後に、同じ title を parentId 付きで検索し、まだ出るかを 1 回だけ確かめる。出るなら以後「ゴミ箱内ファイルが混ざる」前提で動く。
  2. 状態ブロックに `trashed_ids` を持たせ、在庫から除外する。
  3. 確認できるまでは、ゴミ箱移動の提案に「正本側がゴミ箱内でないことを Drive の画面で確認してください」を必ず添える。

### D-02（中）リンク確認の検索が構造的に「ヒットなし」に到達しない・抜ける

- 場所: SKILL §5-7、drive-connector.md §5「被リンク候補」クエリ。
- 問題:
  - a. `fullText` は「title or body text」（TOOLS.md）。旧名で検索すると、改名対象のノート自身がタイトル一致で必ずヒットする。「カルタ設定.md」のような名前の部分一致もヒットする。スニペットは先頭固定（connector §2）で、ヒットが本文のリンクかタイトル一致かを判別できない。→ SKILL の「ヒットなし → Drive で改名してよい」の分岐は、自己ヒットを除外しない限り到達不能。どう除外するかも書かれていない。
  - b. `mimeType = 'text/markdown'` で絞るため、MIME が `text/plain`・`text/x-markdown`・`application/octet-stream` になっている `.md` は素通りする。素通りは「ヒットなし」＝Drive 改名可、という危険側の偽陰性になる。Phase 2 の O（Markdown の判定）も MIME か拡張子かが未規定。
  - c. 検索対象が Markdown だけ。Obsidian の `.canvas`（ノートをパスで参照）、`.base`、`.obsidian/bookmarks.json` などの参照元は見ないまま、確認状態が「検索ベース」に格上げされる。Drive 側の改名では、これらは自動では更新されない。
  - d. 1 改名 1 検索なので、改名候補が N 件なら N 回の検索になる。OR でまとめると、ヒットがどの名前のものか分からなくなる（スニペットが先頭固定のため）。
- 最小の修正:
  - 「自分自身と、タイトルだけの一致は除外し、残りを被リンクの可能性ありとする」と書く。
  - MIME 条件を外し、結果側で拡張子 `.md` に絞る。Markdown の判定は拡張子で行うと明記する。
  - 確認状態の定義に「Markdown 以外の参照元（.canvas 等）は未確認」を加える。
  - 短い名前や一般語（例: 「メモ」）は検索せず、被リンクありの扱いにする。

### D-03（中）重複のゴミ箱移動にリンク確認が要求されていない

- 場所: SKILL §4-1(1)、§4-3、§5-7、不変条件 5。
- 問題: リンク確認の手順（§5-7）は「改名候補ごと」にしか書かれていない。§4-1(1)「完全一致 → 他はゴミ箱へ」と §4-3 は、「他のファイルからリンクされている」を正本選びの基準にするだけで、ゴミ箱に入れる側への被リンクを確認するよう求めていない。
- 失敗シナリオ: 同名の `世界観.md` が別フォルダに 2 つあり、あるノートが `[[設定/世界観]]`（パス付きリンク）で参照している。パスで参照されている側がゴミ箱送りになり、リンクが切れる。添付の重複（同じ画像が 2 つ）でも、`![[…]]` が切れる。
- 最小の修正: §4-1 に「Vault 内のノート・添付をゴミ箱へ移す案では §5-7 のリンク確認を行う。被リンクのある方を正本にする。確認できないなら要確認にする」を 1 文加える。

### D-04（中）衝突確認が Vault 全体の一意性を見ていない。確認の呼び出しも多い

- 場所: SKILL §6-2 手順 1・2、§5-3「Vault 内でファイル名が一意であること」。
- 問題:
  - a. §5-3 は Vault 内の一意性を最優先とするが、§6-2-2 の衝突確認は移動先・同一親（`title = '…' and parentId = '移動先'`）だけ。Vault 内の別フォルダに同名ノートがあると `[[名前]]` が曖昧になる。
  - b. 改名・移動 1 件ごとに衝突確認 1 回、ID ごとに `get_file_metadata` 1 回、では 200 件の改名で 400 回規模になる。§3-1 の「まとめて検索する」方針に反する。Phase 1 の在庫は既に手元にあり、NFKC で正規化済みで、衝突判定に使える。`title =` の検索は NFC/NFD や大文字小文字の差を見逃す。
- 最小の修正: 衝突確認は在庫（NFKC・大文字小文字無視）に対して Vault 全体で行う。事前確認は「対象フォルダを OR でまとめて再取得」1 系統にして、そこで鮮度確認と衝突確認を兼ねる。ゴミ箱移動の対象だけ、必要なら個別に確かめる。

### D-05（中）「完全一致」の判定が目視に依存し、読取の途切れとサイズ不一致への備えがない

- 場所: SKILL §4-1(1)、§7-1「高」、§3-3。
- 問題:
  - a. 「本文が一致」は Claude が 2 つの本文を読んで判定する。MCP の応答をシェルに渡す橋がないので、機械的な照合はできない。表の数値 1 か所や 1 行の追記を見落とすと「完全一致・高」となり、ゴミ箱提案に進む。
  - b. `read_file_content` は「大きいファイルでは不完全になりうる」（TOOLS.md）。同じ位置で途切れた 2 つは、一致して見える。§3-3 の 10 万字という閾値は目安で、途切れの検出手順はない。
  - c. 非ネイティブ形式で `fileSize` が違うのに本文が同一に見える場合の扱いが未規定。バイト一致ではないのに「完全一致」になりうる。
- 最小の修正: 「高」の条件に「非ネイティブ形式では `fileSize` も一致する（または差の理由が説明できる）」を加える。サイズ不一致で本文が同一に見える場合は分類 2 以下・確度「中」にする。末尾が途切れていないこと、見出し数や概算の文字数を根拠欄に書くこと、を求める。

### D-06（中）Frontmatter のパッチをスニペットから作る設計が、既存キーの欠落と文字化けを招く

- 場所: SKILL §5-8(1)「変更後の YAML を示し」、templates §1「適用後の Frontmatter（ファイルごと）」、SKILL §5-2・§3-3（スニペットはエスケープ表現）。
- 問題: 材料は BRIEF スニペット（約 1000 文字、エスケープ済み、絵文字は文字化けしうる）。Frontmatter が 1000 文字を超える、閉じの `---` が見えていない、複数行の値・コメント・プラグイン用キーがある、といった場合に「適用後の YAML 全体」を出すと、ユーザーがそれを貼り替えたとき既存キーが消えたり、文字化けが混入したりする。§5-4「既存の意味のあるキーを削除しない」、不変条件 6 に反する結果になる。
- 最小の修正: パッチは「追加・置換する行だけ」を示す。YAML 全体を示すのは、閉じの `---` まで読めていて文字化けがないときに限る。

### D-07（中）状態ブロックをエスケープ表現で読み戻すため、Drive ID が壊れて見える

- 場所: SKILL §9、templates §3、drive-connector.md §3。
- 問題: 状態ブロック（フォルダ ID・ファイル ID・YAML）は `.md` で保存され、次回は `read_file_content` で読まれる。この表現は `_` `-` `[` `#` `---` などをエスケープする（connector §3）。Drive の ID には `_` と `-` が多く含まれるので、`1aB\_cD\-eF` のように見える。LLM が毎回正しく戻す保証はなく、戻し忘れると `parentId` 検索が空を返し、「前回のフォルダが消えた」「pending が存在しない」と誤認する。SKILL 自身が「書き戻しや原文比較に使わない」と警告している経路を、機械状態の受け渡しに使っている。
- 付随: 「名前が最も新しいログ」を取る方法がない。検索に並び替えがなく、ログが日次で増えると全件をページングすることになる。
- 最小の修正: 保存直後に 1 回読み戻して、ID の往復一致を確認する。「状態ブロックを読むときは、ID 中のバックスラッシュを除去してから使う」を明記する。範囲の ID は使う前に `get_file_metadata` で 1 件確かめる。最新ログは `parentId = 'ログ' and createdTime > '35 日前'` のように期間で絞る。

### D-08（中）差分クエリの範囲判定・`last_scan` の定義・ログ自身の混入

- 場所: SKILL §9「差分の処理 1」、templates §3 の状態ブロック。
- 問題:
  - a. `modifiedTime > last_scan` の結果は Drive 全体から返る。「範囲外は既知のフォルダ ID で除く」とあるが、状態ブロックには範囲のルート ID と除外フォルダしかない。サブフォルダの ID 一覧や親チェーンがないので、深い階層の変更ファイルが範囲内かを判定できない。判定するにはフォルダを再列挙する必要があるが、その手順が書かれていない。
  - b. 除外フォルダ（node_modules など）配下の大量の更新も、クエリでは除外できず、毎回コンテキストに入る。
  - c. `last_scan` の注記「この実行で差分の基準にした時刻」は、「今回使った基準（＝前回の last_scan）」とも読める。そう読むと、次回の基準が進まない。実行の開始時刻と書くべきかどうかも不明。
  - d. ログ用フォルダ（`_drive-organizer-logs`）が除外リストにない。前回のログは、前回の開始時刻より後に作られるので、毎回「新しいファイル」として拾われる。
- 最小の修正: `last_scan` を「この実行の開始時刻（UTC）」と定義する。状態ブロックに `folder_index`（フォルダ ID → 親）を持つか、初回に `mimeType = 'application/vnd.google-apps.folder'` の全件取得で作る手順を書く。ログフォルダを常に除外リストに入れる。

### D-09（中）定期実行で出した提案を承認・実行・却下記録する経路がない

- 場所: SKILL §0-2・§6・§9、templates §1（「ID は内部で保持する」）・§3（`pending`・`declined`）。
- 問題:
  - a. 定期実行は提案をログに書くだけで終わる。承認は誰がどこで行うのか、対話セッションが最新ログを読む手順が §0-2 にない（ログを読むのは §9 の定期実行だけ）。
  - b. `pending` の例は trash だけで、移動先・新しい名前・変更後の YAML を持たない。
  - c. 整理案が 50 件を超えると、整理案ファイルを Drive に保存する（templates §1）が、「ID は内部で保持する」ため、保存されたファイルに ID がない。後日のセッションでは、同名ファイルはパスでは特定できない。
  - d. `declined` を書く経路がない。ログは追記も上書きもできず、新規作成のみ。
- 失敗シナリオ: 定期実行が提案を出す → ユーザーが対話で「D2 と R3 を進めて」と言う → Claude はその ID が何を指すか知らない。あるいは却下しても、次回また同じ提案が出る。
- 最小の修正: 対話の開始時に「ログ用フォルダに未処理の pending があれば最新ログを読む」を 1 行加える。保存する整理案ファイルに ID を含める。承認・却下の後に新しい状態ログを 1 件書く。

### D-10（中）Chat のみの環境でフォルダ単位に区切ると、フォルダをまたぐ重複が検出できない

- 場所: SKILL §3-2「フォルダ単位で区切って進め、各回の結果を作業ログで引き継ぐ」。
- 問題: 作業ログ（templates §2）は件数と結論しか持たず、ファイル単位の名前・サイズ・更新日時を持たない。2 回目以降は、前回分との S/N/Z 照合ができない。最も価値の高い「未整理 と Vault にある同じファイル」のようなフォルダ間の重複が、構造的に見つからない。また、1000 件のメタデータは約 50 万文字（§3-2 の 500 文字 × 1000）で、コード実行がない環境では目視で S/N/V/Z を判定するしかない。
- 最小の修正: Chat のみの環境では、最初に「フォルダをまたぐ重複は検出対象外」と宣言する。または、各回の末尾に「照合用キー（正規化名｜サイズ｜更新日時｜ID の下 6 桁）」の圧縮リストを持ち越す。件数の上限（例: 400 件超は範囲を狭めるようユーザーに提案する）を決める。

### D-11（中）規約把握のサンプリングに上限がなく、本文読取の予算の外にある

- 場所: SKILL §5-2「ノートの種類（フォルダ）ごとに 10 件程度、1 フォルダ 1 回」。
- 問題: フォルダが 30〜40 ある Vault では、30〜40 回 × 10 件 × 1000 文字 ＝ 30〜40 万文字になる。§3-3 の「本文は 30 件程度まで」に数えられない別枠になっていて、方針（読む量を絞る）とずれる。`pageSize` の指定がないと 30 件返る（約 3 万文字/回）。また、ファイル名のパターンは在庫から無料で集計できるのに、スニペットで調べる書き方になっている。
- 最小の修正: ファイル名の規約は在庫から集計し、スニペットは Frontmatter・タグ・type の規約だけに使う。`pageSize: 5〜10` を指定する。対象フォルダは「変更案が出るフォルダ＋主要な数フォルダ」に限り、合計の上限（例: 8 フォルダ）を決める。

### D-12（中）要件が挙げる候補が抽出されない（名前が近い・外れ値・フォルダ丸ごと複製・意図的な複製）

- 場所: SKILL §2 Phase 2、find_candidates.py。要件 §3 Phase 2、§5、§20 の A・C・H。
- 問題:
  - a. 要件が挙げる次の候補を抽出する記号が、SKILL にもスクリプトにもない。「ファイル名が非常に近い」「同じフォルダ・近い更新日時」「同一テーマの大量ファイル」「命名規則から大きく外れたファイル」。V は印語の除去に依存する。「世界観.md」と「世界観設定.md」（ケース A・C）は、サイズ一致（Z）でしか拾えない。少し編集された別名コピーは検出されない。
  - b. ネイティブ形式（Google ドキュメントなど）は S・Z の根拠にできない（SKILL §2）。名前が違う内容重複は構造的に検出されないが、その限界の明記がない。
  - c. フォルダ丸ごとの複製（「…のコピー」フォルダ、Vault のバックアップ）では、何百もの S/N グループが 1 組のフォルダ対に集中する。SKILL はグループごとに本文比較を求めるので、30 件の上限で頓挫するか、何百件ものゴミ箱提案になる。
  - d. Backup・Archive・Templates などのフォルダ内の複製は意図的な可能性が高いが、その判別規則がない。§7-1 の「作成目的に依存する → 要確認」は、内容が完全一致だと働かず、「高」になりうる。
- 最小の修正:
  - スクリプトに P（同一フォルダ内で正規化名の前方一致、または類似度 0.85 以上）を追加する。
  - 「同じフォルダ対に S/N が 5 グループ以上 → フォルダ複製の疑い」を集約して出力する。
  - SKILL に「フォルダ複製は個別に提案せず、Q を 1 件とサンプル 3 対の比較にする」を書く。
  - `Backup`・`Archive`・`バックアップ`・`アーカイブ` などの名前のフォルダ内の複製は要確認にする。
  - ネイティブ形式の内容重複は検出の限界と明記する。

### D-13（中）ローカルでファイルが見える環境で、ハッシュ・grep を使わない

- 場所: SKILL §0-1、§5-8（ローカルの直接編集は Frontmatter の適用にしか使わない）、compatibility。
- 問題: Cowork や Claude Code で Vault（Drive 同期フォルダ）がローカルに見える場合、次のことがコネクタ経由よりはるかに安く確実にできる。
  - `sha256` による完全一致の機械判定（本文の読取 0 回。D-05 が解消する）。
  - `grep -r '\[\[旧名'` による被リンクの網羅的な確認（D-02 が解消し、「確認済み」に到達できる）。
  - 改名に伴うリンクの書き換え。
  現状の既定は、最も弱い方法（目視の本文比較、1 改名 1 検索）。
- 最小の修正: §0-1 に「Vault や Drive の同期フォルダがローカルで読めるなら、重複の判定とリンク確認はハッシュ・grep で先に行う。読取が目的なら検出だけに使い、変更は承認後にコネクタか §5-8 で行う」を 3 行で加える。

### D-14（中）find_candidates.py の V が、日本語の括弧付き版印を拾えず、誤グループを作る

実行して確認した結果:

- `企画書（最終版）.docx`・`企画書【最新】.docx` が、`企画書.docx` と V でまとまらなかった。`VERSION_MARKERS` は語が末尾にあることを前提とし、括弧付きの印（`（最終版）`、`【最新】`）を扱わない。日本語のファイル名では非常に多い形。SKILL の V の説明（「最終版」「最新版」「改訂版」など）から利用者が期待する検出が抜ける。
- `[\s_-]*` が 0 幅で、単語境界がない。`Inv001.pdf`／`Inv002.pdf`、`Rev2.md`／`Rev3.md`、`Semifinal.md`／`Semi.md` が V グループになった（それぞれ `in`・`re`・`semi` に潰れる）。`Server2` や `Driver2` も同様。1000 件超でノイズの元になる。
- 最小の修正: 版印の前に区切り（`(?:^|[\s_\-.(（【\[])`）を必須にする。括弧付きの印（`[（(【\[]…[）)】\]]$`）を追加する。

### D-15（軽微）L の時間語の判定が、正当な名前まで拾う

- 実行結果: `最終章.md`、`copyright.md`、`新規事業計画.docx` が、すべて「時間で意味が変わる語・コピーの印」になった。`TIME_RELATIVE` が裸の `最終|最新|新規|copy|コピー` を部分一致で見る。SKILL §5-3 の語のリストにも、裸の「新規」がある。
- 影響: 小説 Vault の「最終章」「最終決戦」が改名候補になり、§5-3 の「適切な名前は改名しない」と衝突する。一方で、スクリプトの出力を「候補であり、判定ではない」とする注意はあり、致命的ではない。
- 最小の修正: 語を「版・状態を表す形」（`最終版|最新版|最終稿|final|latest` が語として独立、`copy` が語として独立、`のコピー`）に絞る。SKILL に「語が主題の一部か、版印かを内容で判断する」を 1 文加える。

### D-16（軽微）TSV の読み込みが `"` で始まるタイトルで黙って壊れる。`--me` の入手方法がない

- 実行結果: `"最終 draft.md` のようにタイトルが `"` で始まる行が 1 件あると、後続の 5 行がその 1 件に吸収された。入力 6 件が 2 件になり、タイトルが 214 文字の 1 件に化けた（エラーも警告もない）。`csv.DictReader` の既定の引用処理が原因。在庫が黙って欠落するため、以後の判定がすべて狂う。
- 最小の修正: `csv.DictReader(f, delimiter="\t", quoting=csv.QUOTE_NONE)`。あわせて、入力件数を `wc -l` と照合する。
- 付随: `--me` にはメールアドレスが要るが、SKILL に入手方法がない。`owner = 'me'` の検索を pageSize 1 で 1 回行い、`owner` を読む、と 1 行書けばよい。

### D-17（軽微）§0-1 の矛盾

- 場所: SKILL §0-1 の表「検索・一覧: 必須。接続を依頼して終了」と、末尾の箇条「コネクタがなければ、ユーザーが用意した一覧を材料に提案だけ行う」。compatibility は「コネクタが必要」。
- 影響: どちらで動くか、実行するモデルによって分かれる。
- 最小の修正: どちらかに統一する。「コネクタなしでも、ユーザーが一覧を渡したら提案だけ行う」を残すなら、表の「ないとき」を「一覧の提供を依頼。提供があれば提案のみ」とする。

### D-18（軽微）Obsidian 以外のファイルの改名方針がない

- 場所: SKILL §2 Phase 2（L は全ファイル対象）、§5-3（Obsidian 用の命名規則）、§4 Phase 4。
- 問題: 非 Obsidian ファイル（docx・pdf・Google ドキュメント）の改名にどの規則を使うかが書かれていない。§5-3 を類推すると、「報告書_最終版2.docx」を `v01` へ改名する案が出て、依頼のない大量改名になる。要件 §14「好みだけの変更をしない」に反する方向。
- 最小の修正: 「Obsidian 以外のファイルは、ユーザーの依頼があるとき、または重複の解消に必要なときだけ改名を提案する。§5-3 の規則は適用しない」を §5 の冒頭に 1 文加える。

### D-19（軽微）§4-2 と §4-1(3) の断定

- 「一方が他方の内容をすべて含み、追記があるなら、追記がある方が新しい」（§4-2）は断定しすぎ。A ⊃ B のとき、B が「削除で新しくなった版」である可能性がある。更新日時を補助にとどめる方針と組み合わせると、実際には新しい方に `_v01`（旧版）を付ける誤ったラベルになりうる。「新しい可能性が高い（確度は中）。更新日時と矛盾するなら分岐として Q にする」とする。
- §4-1(3)「旧版はアーカイブへの移動を提案」は、Phase 4「新しいフォルダは同じ分類のファイルが 3 件以上あるときだけ」と衝突する（1 組のために Archive フォルダは作れない）。既存の Archive がなければ `_v01` への改名だけを提案する、と決めておく。

### D-20（軽微）旧名を aliases に残す F と改名 R が対になっていない（ケース G）

- SKILL §5-4 は「旧名のうち意味のあるもの」を aliases に入れるとするが、改名（R）と alias 追加（F）を対にする規則がない。Drive 側の改名（被リンクなし）で F を承認し忘れると、旧名が検索から消える。
- 最小の修正: 「旧名を aliases に残す価値がある改名は、R と F を 1 つの承認単位（R1+F1）として出す」と書く。

### D-21（軽微）U の「必ず比較」と 30 件の上限、無人実行での超過

- SKILL §2 は U を「必ず本文を比較する」とし、§3-3 は本文の読取を 30 件程度までとして、超えるときはユーザーに尋ねる。U が 30 件を超える場合、両者が衝突する。無人の定期実行では「尋ねる」ができないが、§9 に超過時の扱いがない。
- 最小の修正: 超過分は `open_items` に入れて次回へ持ち越す、と §3-3 か §9 に 1 行書く。

### D-22（軽微）承認と並び順の曖昧さ

- §6-1「20 件を超える改名・移動 → 影響件数と例を示して明示的な承認」。整理案（ID 一覧つき）に「全部」と返信すれば明示的な承認なのか、もう一度確認するのか、読み取れない。「整理案への承認がこれを兼ねる。ただし『全部』で 20 件超のときは件数を再掲して確認する」など、どちらかに決める。
- Phase 5「§7 の優先度順に並べる」と、templates のカテゴリ別テーブル（重複・改名・Frontmatter・移動・要確認）が競合する。「各テーブル内を優先度順に」と一文足す。

### D-23（軽微）無人実行の禁止リストに Vault 内ファイルの移動がない

- §9 は「ゴミ箱への移動、Vault 内の Markdown の改名、Frontmatter の適用」を無人では実行しないとするが、Vault 内 Markdown・添付の移動は許可のまま。§5-7 で、パス付きリンクや Markdown 形式のリンクは移動で切れると書いており、Vault のリンク形式の確認（サンプルの読取）は人がいないと省かれやすい。
- 最小の修正: 禁止リストに「Vault 内のファイルの移動」を加える。

### D-24（軽微）冗長さと日本語の細部

- 同じ規則の反復:
  - 「コネクタで本文を書き換えない」が冒頭の 3 点、§0-1、§1-4、§5-8、§6-1 で 5 回。
  - ゴミ箱の規則が §0-2、§1-1、§6-1、§7-1、§9 で 5 回。

## 5. 良く設計されていて、壊してはいけない点（5 つ）

1. **段階的な読取のはしご（§2 Phase 3、§3）**: メタデータ → BRIEF スニペット → 特徴的な一節の `fullText` 検索 → 全文、と安い順に使い、判断がつけば止める。一覧は `excludeContentSnippets: true` と pageSize 30 の実測値、複数フォルダの OR まとめ、読んだファイルの要約メモ、で構成されている。要件 §2 の中核を、実コネクタの制約（pageSize の実測上限、スニペットが先頭固定）に合わせて具体化できている。
2. **安全の不変条件（§1）と、ツール面に合わせた割り切り**: 完全削除ツールがないことを前提にした「ゴミ箱のみ」、本文を書き換えない（「新規作成して旧をゴミ箱へ」という置き換えも禁止）、確度「高」のみゴミ箱、実行直前の事前確認、順序（作成 → 移動 → 改名 → ゴミ箱）。「効率化を理由に省略しない」と明記されている点も適切。
3. **Obsidian の事実関係の正確さ（§5-4・§5-7）**: aliases に旧名を入れても既存の `[[旧名]]` は解決されない、Drive 側の改名ではリンクが自動更新されない、Drive 上の `.md` は `title` に拡張子を含める、Daily notes はファイル名形式に依存する、単数形の `tag`/`alias` は旧形式、YAML の引用符（`"[[ノート]]"`）。確認状態の 3 段階（確認済み／検索ベース／未確認）と、リンクがあるノートは「Obsidian で改名」に振る設計も良い。
4. **定期実行の設計（§9）**: 状態ブロックによる引き継ぎ、`modifiedTime` と `createdTime` の OR（アップロードでは元の更新日時が残るため）、`declined` による再提案の抑止、履歴がなければ推測しない、無人ではゴミ箱移動・Vault 内の改名・Frontmatter 適用をしない。要件 §18 に忠実。D-07・D-08・D-09 の修正は、この骨格を保ったまま行える。
5. **過剰変更の抑制（§5-1・§5-4・§5-6・§7）**: Vault 内でも改名しない対象（日記ノート・テンプレート・`.excalidraw.md`・自動命名の添付）、aliases 0〜3 個・tags 1〜3 個の目安、date に作成・更新日時を流用しない、「同じ役割なら統一、役割が違うなら維持」、確度による行動の制限（ゴミ箱は「高」のみ）、templates の「変更しないもの」欄。要件 §9・§11・§21 の禁止事項（tags の大量生成、意味のない Frontmatter 追加、強制統一）に対して十分な歯止めになっている。
