## A. 同一内容・異名

**シナリオ**
- `創作/未整理/無題.md`: text/markdown, 1,842 B, modified 2026-03-02T10:15Z, created 2026-08-20, owner me
- `創作/Obsidian/設定/世界観.md`: 1,842 B, modified は同じ, created 2026-03-05
- 内容は同一（先頭: `type: setting` / `tags: [世界観]` の Frontmatter と「アクエラの街は、水の匂いより先に…」）。`創作/Obsidian/.obsidian` があり、Vault ルートは `創作/Obsidian`。未整理は Vault の外。

**トレース**
- 読む
  - メタデータ: `parentId='root'` → 創作 → 創作の子（未整理, Obsidian）の 3〜4 回（§2 Phase 1, §3-1）。
  - Phase 2 で S（同 MIME・サイズ・更新日時）と、`無題` による L が立つ（§2 Phase 2）。
  - 本文: S 候補なので `read_file_content` を 2 回（§3-3, §1-3）。権限: `get_file_permissions` を 2 回（§4-3）。
- 判断
  - 分類 1「完全一致」、確度「高」（§4-1, §7-1）。
  - 正本は §4-3 ①「整理後の置き場所にある」で Vault 側の `世界観.md`。
  - 名前が整っているのも Vault 側。共有されていなければトレース上は問題なし。
- 変更する
  - 承認後に `無題.md` を `trash_file`（§6-1: ゴミ箱は毎回、対象一覧を示して明示承認）。
  - 実行手順は事前確認 1 回 + `trash_file` 1 回（§6-2）。
- 変更しない
  - `世界観.md` は触らない。完全削除もしない。
  - `無題.md` の改名（L）は、D で消す対象なので出さない。ただしこの排他は SKILL に明記がない。
- 承認: 整理案の D1 で。ゴミ箱の復元は Drive の画面と伝える（§1-1）。

**判定: 適切**。全体として安全側に倒れる。

**問題と最小修正**
1. §6-1 は「毎回、対象一覧を示して明示的な承認」と書くが、テンプレートの承認例は「全部」（templates.md §1）。「全部」で D のゴミ箱まで実行してよいかが曖昧。修正案: テンプレートの承認行を「D は名指しで（例: D1）。『全部』にはゴミ箱移動を含めない」とする。
2. §4-3 ②は「他のファイルからリンクされている」を判断材料にするが、リンク検索の手順は §5-7（改名用）にしかない。修正案: 「ゴミ箱候補が Vault 内の Markdown・添付なら、§5-7 の検索で被リンクを確かめる。ヒットがあれば D にせず Q」と一文足す。ただし `無題` のような一般語は誤ヒットが多く、ほぼ常に Q になる点も併記する。
3. 効率: 1,842 B（日本語で約 600 字）は BRIEF スニペット（約 1000 字）で全文が入る。SKILL は「ゴミ箱の判断は全文」（§2 Phase 3 の 4）としか言わず、スニペットが全文を覆う小ファイルの近道を書いていない。修正案: 「サイズが約 2.5KB 未満のテキストは BRIEF スニペットを全文とみなしてよい」。2 回の read を 1 回の検索に減らせる。
4. 仕様上の限界: 同じ内容でも Google ドキュメント（サイズなし）で名前が違うと、S・Z が使えず候補に上がらない（§2 Phase 2 の注記どおり）。U（ユーザー指定）以外では発見できないことを、限界としてどこかに明記するとよい。

## B. 最終版 / 最終版2 / 最新版に差がある

**シナリオ**（`創作/原稿/`、いずれも Google ドキュメント。サイズなし）
- `第1部_最終版`（modified 2026-05-01）: 第 1〜5 章
- `第1部_最終版2`（modified 2026-05-10）: 第 3 章を改稿 + 第 4 章の誤字を修正
- `第1部_最新版`（modified 2026-04-20）: 第 3 章の改稿（最終版2 と同文）+ 第 6 章を追加
- 最新版の更新日時が最も古い。最新版と最終版2 は互いに相手にない内容を持つ。

**トレース**
- 読む
  - メタデータ 3〜4 回。Phase 2 は V（印を除いた基本名 `第1部` が同じ）（§2 Phase 2）。
  - 本文: 3 件を `read_file_content`（§3-3: V は優先度 2 位）。
  - 各 2〜5 万字なら約 10 万字がコンテキストに入る。
  - 特徴的な一節（第 6 章の一文、第 4 章の訂正箇所）で `fullText contains` を 1〜2 回（§2 Phase 3 の 3）。
- 判断
  - §4-2 に従い、名前や更新日時ではなく内容で判断する。
  - 最終版は、最新版・最終版2 のどちらにも包含される旧版（分類 3）。
  - 最新版と最終版2 は互いに相手にない内容があるので**分岐** → 要確認（§4-2）。
- 変更する
  - 最終版だけ、旧版として `_v01` への改名かアーカイブへの移動を提案（§4-1 の分類 3。ゴミ箱は出さない）。
  - フォルダ新設の目安は 3 件以上（§2 Phase 4）なので、改名案（R）になる。
- 変更しない
  - 最新版と最終版2 の統合は行わない（§4-4）。改名も分岐が解けるまで保留。
  - 3 件ともゴミ箱には入れない。
- 承認: R は整理案で。Q1「どちらを正とするか・統合するか」はユーザーに尋ねる。実行は事前確認 1 + 衝突確認 1 + `update_file` 1。
- 呼び出し: 調査 8〜10、実行 +3。

**判定: 条件付きで適切**。分岐の扱いと「名前を信じない」原則は良い。

**問題と最小修正**
1. §4-2「一方が他方の内容をすべて含み、追記があるなら、追記がある方が新しい」は、追記だけの編集を前提にしている。後の版が章を削って短くなった場合、内容の多い古い版を「新しい」と誤判定し、実際の最新版に `_v01` を付ける案を出す。更新日時は「補助」（§4-2）に格下げされていて歯止めにならない。
   修正案: 「包含関係の向きが更新日時・作成日時の順序と逆なら、削除による短縮の可能性があるため、分岐扱いで要確認（確度: 中）にする」。
2. 差分の見つけ方が未規定。数万字 × 3 を会話内で目視比較すると、誤字レベルの差は見落とすか、幻覚で作る。
   修正案: 「差分の根拠には、見出し構成の突き合わせ結果と、差分を示す一節の引用を書く。誤字レベルの差は断定せず『軽微な差あり（未確認）』とする」。
3. Google ドキュメントのコメント・提案モードは `read_file_content` の本文に入らない（`includeComments` 引数はあるが SKILL は触れていない）。版の比較でコメントに履歴がある場合を見落とす。修正案: 「ネイティブ形式の版比較では `includeComments: true` を 1 回だけ試す」。呼び出し増を避けたければ注記だけでもよい。
4. Vault 内の .md で同じ状況になると、R の対象名（最終版など）は §5-3 の対象。この場合はさらに §5-7 のリンク検索が加わり、呼び出しが +2〜3 回。

## C. 同テーマ・用途違いの Markdown

**シナリオ**（Vault `創作/Obsidian`。人物フォルダの規約は `type: character` / `tags: [人物]`）
- `人物/シューニャ.md`: 人物プロフィール（年齢・外見・性格）
- `人物/キャラ_シューニャ.md`: 同じプロフィールの旧稿（一部の記述が古い）
- `設定/シューニャ設定.md`: 能力設定（六炎の一覧）
- `設定/主人公シューニャ.md`: 主人公論のエッセイ
- `人物/Shunya.md`: 英語版プロフィール（翻訳）
- `第02章.md` などから `[[シューニャ設定]]` が張られている。

**トレース**
- 読む
  - メタデータ 3〜4 回。Phase 2 の S・N・V・Z・L では、これらの束が**一つも候補にならない**。名前が正規化後に違い、`_最終版` などの印もなく、サイズも違うため。
  - 束ねるには Claude が一覧を目視するか、`title contains 'シューニャ' or title contains 'Shunya'` を自分で思いつく必要がある。SKILL は §5-6 の例文で「シューニャ」の 5 種を挙げるだけで、見つける手順を書いていない。
  - 見つけた後: 人物フォルダの規約 BRIEF 1 回（§5-2）、5 件の BRIEF 1 回（§2 Phase 3 の 2）、重複が疑われる 2 件の全文 2 回、改名候補のリンク検索 2〜3 回。合計 10〜13 回。
- 判断（§5-6 の「役割は内容で判断」）
  - シューニャ.md と キャラ_シューニャ.md は同役割 → §4 で扱う。旧稿なら分類 3、断定できなければ Q。ゴミ箱は出さない。
  - シューニャ設定（能力）と 主人公シューニャ（エッセイ）は役割が違う → 維持（分類 5）。
  - Shunya は英訳 → 分類 4（原本と派生）。維持。
- 変更する
  - `シューニャ設定` → `シューニャ_能力設定` のように、名前で役割がわかる改名案を出す。被リンクの検索ヒットがあれば「方法: Obsidian で改名」（§5-7）。
  - `Shunya` を `シューニャ.md` の aliases に入れるかは、`Shunya.md` が別ノートとして残るなら入れない。
- 変更しない: 新タグの追加、日本語名の統一、翻訳ノートの統合、役割が違うノートの同名化。
- 承認: R は整理案で。Q（旧稿の扱い）はユーザーに尋ねる。

**判定: 条件付きで適切**。判断ロジック（§5-6, §4-1）は要件どおりで、過剰統一を防げている。

**問題と最小修正**
1. 「同一テーマの束」を作る候補抽出がない。要件 §3 の Phase 2「類似ファイル、同一テーマの大量ファイル」に対応する記号が SKILL にない。
   修正案: Phase 2 の表に「T: 名前に共通の語（人物名・作品名・プロジェクト名）を含むグループ」を加える。手順は「Vault 内のタイトルの共通語を数えて、上位語を `title contains` で束ねる」。`drive-connector.md` §2 のとおり、日本語は途中一致するのでこの検索が使える。
2. `aliases` に入れる語が、既存の別ファイルのファイル名と衝突する場合（`Shunya` など）への注意がない。リンク補完で曖昧になる。修正案: §5-4 aliases に「既存ノートのファイル名と同じ語は入れない」を足す。

## D. Wiki リンクされている Markdown

**シナリオ**
- Vault `創作/Obsidian`。`人物/キャラ_カルタ.md`（規約は「人物名のみ」）に対し、`章/第02章.md` に `[[キャラ_カルタ]]`、`章/第05章.md` に `[[キャラ_カルタ|カルタ]]`、Frontmatter の `related: "[[キャラ_カルタ]]"` を持つノートが 1 つ。
- 同じ人物ノートに `![[カルタ_立ち絵.png]]` の埋め込み。

**トレース**
- 読む
  - メタデータ、規約 BRIEF（§5-2）: 3〜5 回。
  - リンク検索: `fullText contains 'キャラ_カルタ' and mimeType = 'text/markdown'` を 1 回（§5-7）。
  - 確認済みにしたいなら、ヒットしたノートを 1〜2 回 read。ただし §3-3 の 30 件枠を使う。
- 判断
  - §5-3 と規約から改名候補 R1（`カルタ.md`）。ヒットあり → 「被リンクの可能性あり」、状態は「検索ベース」（§5-7）。
  - 方法は「Obsidian で改名」。設定「内部リンクを自動更新」が有効か、ユーザーに確認してもらう。
  - PNG は関係が明確でも触らない（§5-7 の添付。ノートに合わせた改名案は、埋め込み元が特定できたときだけ）。
- 変更する: Drive では何も変更しない（案のみ）。
- 変更しない: 改名そのもの（Drive 側）、PNG、被リンク元のノート本文。
- 承認: R1 を整理案に載せ、ユーザーが Obsidian で実行する。
- 呼び出し: 調査 6〜8。実行 0。

**判定: 適切**。§1-5 と §5-7 が要件 §12 の「断定しない」に沿い、方向が安全。

**問題と最小修正**
1. ヒットがあると「Obsidian で改名」が固定で、ユーザーが「リンク切れは承知で Drive で名前を変えたい」と言った場合の扱いが未規定。改名は元の名前に戻せば直るため、被害は限定的。
   修正案: 「ユーザーがリスクを承知で Drive 側の改名を明示した場合は、切れるリンクの件数と該当ノートを示し、再確認のうえ実行可。ログに旧名を残す」。
2. 検索クエリが `mimeType = 'text/markdown'` に固定（§5-7, connector.md §5）。Drive 上の `.md` の MIME は、アップロード経路や時期で `text/x-markdown` や `application/octet-stream` になりうる。実機では未確認の懸念で、確度は低い。
   修正案: 「ヒット 0 件のときは `mimeType contains 'markdown'` か `title contains '.md'` でも 1 回確かめる」。
3. 名前が短い一般語（例: `世界観`）では、誤ヒットだらけで常に「Obsidian で改名」になる。安全側なので問題はないが、ユーザーの手作業が増えると事前に伝えるとよい。ヒットの中に候補ファイル自身が含まれる点も、「自分自身は除く」と書くと親切。

## E. Vault のルールと異なる Frontmatter

**シナリオ**（`創作/Obsidian/人物/` の 14 ノート）
- 多数派 9 件: `type: character` / `tags:` をブロックリストで `- 人物` / `aliases: []`
- `ペトロス.md`: `tag: 人物`（単数）
- `カルタ.md`: `Tags: 人物, 主人公`（大文字・カンマ区切り）
- `ラナ.md`: Frontmatter なし
- `アクエラ.md`: `type: キャラクター`
- `シューニャ.md`: `cssclass: wide` とプラグインのキー

**トレース**
- 読む
  - メタデータ 3〜4 回。規約把握: `parentId = '人物' and mimeType = 'text/markdown'` を BRIEF で 1 回（§5-2）。14 件は 1 ページに収まるので、逸脱ノートもこの 1 回で全部見える。
  - `read_file_content` は 0 回。合計 5〜7 回。
- 判断
  - 規約メモ: `type: character`、`tags` はブロックリスト（人物）、`aliases` あり。
  - F1 `tag` → `tags`（確度 高）。F2 `Tags: 人物, 主人公` → `tags` のリスト。ただし `主人公` は既存の値なので消さない（§5-4「既存の意味のあるキーを削除しない」）。この値が Vault で他に使われているかは Q にできる。
  - F3 `ラナ.md` の Frontmatter 追加は優先度 3（§7-2）。同種ノートとの統一（§5-6）で確度 中。
  - F4 `type: キャラクター` → `character`（中）。
- 変更する: Drive では何も変更しない。コネクタは本文を書き換えられないため（§1-4, §5-8）、変更後の YAML をパッチとして渡す。Vault のローカルフォルダにファイルツールで届く環境なら、承認後に Frontmatter だけを編集し、本文が変わっていないことを確かめる。
- 変更しない: `cssclass`（旧形式の移行は Vault 全体の規約変更として別提案・件数つき、§5-4）、プラグインのキー、`シューニャ.md` の本文、日記・テンプレート。
- 承認: 5 件なので 20 件しきい値（§6-1）には届かない。F の一括承認（「F 以外」など）で足りる。

**判定: 条件付きで適切**。「規約を上書きしない」「値を勝手に消さない」がきちんと効く。

**問題と最小修正**
1. 逸脱の検出範囲が曖昧。§5-2 は規約を作るために「ノートの種類ごとに 10 件程度」をサンプルすると読める。E の目的は逸脱ノートを見つけることで、サンプルでは取りこぼす。全数を見るなら、300 ノートで BRIEF が 10 回、約 30 万字。
   修正案: §5-2 に「規約の推定は 10 件のサンプルでよい。逸脱の検出は、ユーザーが範囲に指定したフォルダの全ノートの BRIEF を 30 件ずつ走査する。件数 × 約 1000 字を先に見積もり、大きければフォルダ単位に区切る」と足す。
2. パッチの手作業適用が重い。40 ノートで F が 40 件なら、ユーザーが Obsidian で 40 回貼り替えることになる（Drive のみの環境）。

3. スニペットは Markdown 記号がエスケープされた表現（`\-`, `\---`）で、インデント幅などが失われる。パッチの YAML はこの表現から書き起こすため、インデントの流儀（2 スペースか 4 か）を規約メモに含めるとよい。

## 11. 追加のエッジケース（実際に SKILL が弱い点）

### X1. 定期実行で「検討済み・維持」の判定が状態ブロックに残らない
- 状況: 毎週の定期実行。C/H/I のように、分類 4（原本と派生）・分類 5（関連するが別物）と判定して「両方残す」と決めたペアがある。J の「そのまま残す」との回答も同じ。

### X2. 大きなファイルの事前ガードが実行できない
- 状況: 42 ページの PDF、数万字の Google ドキュメント、数百 KB の Word など。
- SKILL の動き: §3-3 は「本文 10 万字超は全文を読まず、先頭と一節検索で判断」と言う。しかし `read_file_content` には長さの上限・オフセットの引数がなく（TOOLS.md）、読む前に文字数を知る方法もない。Google ネイティブ形式にはサイズがない。実際には「読んでから 10 万字超だと知る」ことになり、コンテキストを先に消費する。§3-3 の「サブエージェントが使える環境では比較を任せる」は Chat では使えない。
- 影響: B・I で顕著。分類 1 の確認にはどのみち全文が要るので、ゴミ箱の判断は特に重い。
- 最小修正: 「読む前の目安: 非ネイティブなら `fileSize` が約 1MB（PDF）/ 300KB（Office）を超える場合、ネイティブ形式は BRIEF が 1000 字で切れて続きがある場合は、全文を読まず、BRIEF + `fullText` の一節検索だけで確度『中』止まりにする」。

### X3. ゴミ箱候補がショートカットの参照先になっている
- 状況: `プロジェクトA/資料.pdf`（ショートカット）が `未整理/資料.pdf`（実体）を指している。実体と、`アーカイブ/資料.pdf` が完全一致で、正本を後者にしてゴミ箱案が出る。
- SKILL の動き: ショートカットは「変更しない（報告のみ）」（§0-3）で、候補抽出でも除かれる（find_candidates.py の N・V）。コネクタの返却項目にショートカットの参照先 ID はない（connector.md §1）。ゴミ箱の対象がショートカットの参照先かを確かめる手順がなく、実行後にショートカットが壊れる。ゴミ箱に入れるので取り返しはつくが、案の時点で防げる。
- 最小修正: §4-3 に「ゴミ箱候補と同名（正規化後）のショートカットがインベントリにあれば、参照先の可能性があるので Q にする（または警告を付ける）」を一行足す。
