# Drive Organizer & Obsidian Optimizer

Google Drive の大量ファイルを「メタデータ → 候補 → 必要な本文だけ」の順に調べ、承認された変更だけを実行する。Obsidian 用の Markdown は、既存 Vault の規約に合わせてファイル名と Frontmatter を整える。

## 参照ファイル

条件に当てはまるときだけ読む。一度読んだものは読み直さない。

| ファイル | 読む条件 |
|---|---|
| `references/drive-connector.md` | 常に。Drive を調べる前に |
| `references/obsidian.md` | Obsidian 対象の Markdown について、改名・移動・ゴミ箱・Frontmatter の案を作る、または実行するとき |
| `references/templates.md` | 整理案か作業ログを書くとき |
| `references/scheduled.md` | 定期実行のとき。または対話で前回の整理案の ID を指され、その内容が会話にないとき |
| `scripts/find_candidates.py` | インベントリが 300 件を超え、コードを実行できるとき（使い方は `--help`） |

## 0. 開始前チェック

### 0-1. 使えるツール

ツール名の接頭辞は環境によって異なる。存在しないツールや権限を前提にしない。

| 能力 | ツール | ないとき |
|---|---|---|
| 検索・一覧 | `search_files`, `list_recent_files` | 接続を依頼する。ユーザーが一覧を用意すれば、それを材料に提案だけ行う |
| 本文 | `read_file_content` | 本文を比較できないので確度を下げる |
| 改名・移動 | `update_file`（変更できるのは `title` と `parentId` だけ） | 提案のみ |
| ゴミ箱へ移動 | `trash_file`（完全削除と復元のツールはない） | 提案のみ |
| 作成 | `create_file`（フォルダ、ログ） | ログは返答に書く |
| 共有の確認 | `get_file_permissions` | 共有の有無は要確認とする |

コネクタでは本文を書き換えられない（Frontmatter の適用方法は `references/obsidian.md` §7）。ブラウザ操作で大量整理をしない。

### 0-2. 実行形態と依頼の範囲

- **対話**: 整理案を出し、承認された項目だけを実行する。
- **定期実行**（その場に人がいない）: 原則として提案のみ（`references/scheduled.md`）。
- 対象と操作の具体的な指示（「A を B フォルダへ移動して」）は、その指示を承認とみなす。ただしゴミ箱への移動は §6-1 に従う。
- 依頼が一部（重複の調査だけ、など）なら、調査も整理案もその範囲に絞る。「何も変更しないで」と言われたら、ログのファイルも作らない。

### 0-3. 範囲と除外

- 指定フォルダの配下。「Drive 全体」ならマイドライブ（`parentId = 'root'`）から幅優先で下る。条件なしで Drive 全体を検索しない（除外フォルダの中身まで拾うため）。
- 範囲外のフォルダは、移動先の候補として子を一覧するだけにとどめ、中身を調査しない。
- 他人がオーナーのファイルとショートカットは変更しない（報告のみ）。
- 次のフォルダは中身を列挙せず「除外」と記録する。中を動かすとアプリやビルドが壊れ、列挙しても件数が膨らむだけのため。
  - アプリが管理するフォルダ: `.obsidian`, `.trash`, `.git`, `Google AI Studio`, `Colab Notebooks` など
  - コード関連: `node_modules`, `.venv`, `venv`, `__pycache__`, `dist`, `build`、および `package.json`・`pyproject.toml`・`.git` を直下に持つフォルダ
  - このSkillのログ用フォルダ
- ファイルに書き出せないチャットだけの環境では、1 回の会話で扱うのは 500 件程度までを目安にし、超えるならフォルダ単位で区切る。区切るとフォルダをまたぐ重複を見つけにくくなることを、最初に伝える。

## 1. 安全の不変条件

効率化を理由に省略しない。

1. 完全削除はしない。不要なものは承認後に**ゴミ箱へ移す**。復元は Drive の画面から行う（通常 30 日以内）と伝える。
2. 重複グループからは必ず 1 件以上を残す。互いを消し合う操作を組まない。
3. 名前・サイズ・日時だけで重複と確定しない。確定には本文の比較が要る（§4）。
4. コネクタで本文を書き換えない。「新しく作って旧ファイルをゴミ箱へ」という置き換えもしない（ファイル ID・版の履歴・共有設定が失われ、書き写す過程で本文が変わるおそれがあるため）。
5. 被リンクを確かめきれないノートについて「リンクは壊れない」と言わない。Drive 側での改名やゴミ箱移動は、`[[リンク]]` を書き換えない。
6. 既存 Vault の規約（命名、キー名、タグ体系）を上書きしない。規約そのものを変える提案は、影響件数を示して別に承認を取る。
7. 実行の直前に、対象が整理案の時点から変わっていないことを確かめる。変わっていれば、その項目は実行しない。
8. 承認された方法を変えない。「Obsidian で改名」とした項目は、実行を頼まれても Drive で改名せず、手順を案内する。

## 2. ワークフロー

### Phase 1: 全体把握（メタデータのみ）

- 複数フォルダの子を 1 回の検索でまとめて取る（`parentId = 'A' or parentId = 'B' …`、`excludeContentSnippets: true`、pageSize 30）。
- 結果から**インベントリ**（ID、タイトル、MIME、サイズ、作成・更新日時、親、オーナー）を作り、以後の判断はすべてこれを使う。取得済みのファイルに `get_file_metadata` を重ねない。
- `.obsidian` を直下に持つフォルダを **Vault ルート**として記録する。

### Phase 2: 候補抽出（インベントリだけで）

| 記号 | 候補 | 補足 |
|---|---|---|
| U | ユーザーが重複を疑っているファイル | 最優先。必ず本文を比較する |
| S | 同じ MIME・サイズ・更新日時 | 同じ元ファイルのアップロード複製の可能性が高い |
| N | 正規化した名前が同じ | 重複とは限らない |
| V | 印を除くと同じ基本名 | 印の例: 「(1)」「のコピー」「Copy of」「最終版」「最新版」「final」「v2」、派生の「要約」「抜粋」「圧縮版」 |
| P | 同じフォルダで名前が非常に近い | 連番（数字だけの違い）は除く |
| Z | 同じ MIME・サイズ（1KB 以上）で名前が違う | 名前を変えた複製の可能性 |
| F | 2 つのフォルダの間に S・N の組が多数ある | フォルダごとの複製。まとめて要確認 1 件にする |
| T | 同じ語を名前に含むまとまり | 同一テーマの大量ファイル。一貫性の確認に使う |
| L | 命名の問題 | 無題、余分な空白、使えない文字、Notion 書き出しの 32 桁 ID、長すぎる名前、時間で意味が変わる語 |
| O | Obsidian 対象と思われる Markdown | §5 |
| X | 空・異常なファイル | 0 バイト、拡張子と MIME の不一致など。要確認 |

- 名前は、NFKC 正規化・大文字小文字の無視・前後の空白の除去をしてから比べる。「(1)」などの記号は検索では拾えない（記号が無視される）ので、印の判定はインベントリに対して行う。
- ネイティブ形式（Google ドキュメントなど）はサイズが本文量と対応しないので、S・Z の根拠にしない。名前の違うネイティブ形式どうしの重複はここでは見つからない。検出の限界として報告に書き、名前の中の日付や作成日時の近さを手がかりにする。
- 300 件を超え、コードを実行できる環境では、インベントリを TSV に書き出して `scripts/find_candidates.py` で抽出する。TSV には必要な列だけを書き、検索結果の JSON を丸ごと写さない（写した量がそのままトークンの消費になる）。ID は重ならない範囲で先頭 10 文字程度に縮めてよい（実行に使う完全な ID は、§6-2 の事前確認で取り直す）。出力は候補であり、判定ではない。

### Phase 3: 詳細確認（必要なものだけ）

安い方法から順に使い、判断がついたらそこで止める。

1. 取得済みのメタデータ
2. 先頭: `snippetVerbosity: 'BRIEF'` の検索で、複数ファイルの先頭（約 1000 文字）を 1 回で取る。Frontmatter はたいていここに入る。末尾が `...` で切れておらず上限にも届いていない小さなファイルは、ネイティブ形式でも全文とみなしてよい（両方をこの方法で取れば、本文の比較になる）。
3. 特徴的な一節での全文検索（`fullText contains '…'`）: 派生や転記を 1 回で探せる。
4. 全文（`read_file_content`）: ゴミ箱への移動や原本の特定など、判断がこれに依存するときだけ。

読んだファイルは要約メモ（見出し構成、Frontmatter、主な差分、外向きのリンク）に残し、二度読まない。

### Phase 4: 分析

- 重複の分類と正本の選定は §4、Obsidian のファイル名・Frontmatter・リンクは §5。
- 移動先は既存のフォルダ構成を優先する。新しいフォルダは、同じ分類のファイルが 3 件以上あり、置き場所がないときだけ作る。階層を深くしない。
- Obsidian 対象でないファイルの改名は、優先度 1 の問題（§7-2。重複グループの旧版に `_v01` を付けるなどを含む）か、ユーザーの依頼があるときに限る。

### Phase 5: 整理案

`references/templates.md` の形式で出す。各項目に ID（D=重複、R=改名、F=Frontmatter、M=移動、Q=要確認）を付け、各表の中は優先度の順に並べる。変更が不要なら、そう伝えて終える。

### Phase 6: 実行

承認された項目だけを §6 の手順で実行し、作業ログを残す（§8）。

## 3. 読む量の管理

- 着手前に、件数から量を見積もる（メタデータ 1 件で約 500 文字、BRIEF 1 件で約 1000 文字）。
- 全文の取得は、1 回の実行で合計 30 件程度まで（BRIEF は数えない）。優先順は U、S、V、Z、N。超えそうなら残りを要確認にし、対話では続けるかを尋ね、定期実行では次回へ持ち越す。
- 読む前に大きさを見積もる。`fileSize` の大きいもの（目安: PDF 1MB 超、Office とテキスト 300KB 超）や、BRIEF の後に長い続きがあるネイティブ形式は、全文を読まない。先頭と一節の検索で判断し、確度は「中」までとする。
- `read_file_content` は Markdown の記号をエスケープした表現で返す（`\#`, `\-`, `\---` など）。比較は同じ取得方法どうしで行い、原文として扱わない。`download_file_content`（原文の base64）は、小さなテキスト（目安 50KB 以下）で原文そのものが必要なときだけ使う。
- Vault や同期フォルダをローカルで読める環境では、完全一致はハッシュで、被リンクは grep で確かめる。本文をコンテキストに入れずに済み、確実でもある。
- ファイルに書き出せる環境では、インベントリと要約メモをファイルに置き、会話の中で持ち回らない。

## 4. 重複判定

### 4-1. 分類

| 分類 | 基準 | 既定の推奨アクション |
|---|---|---|
| 1. 完全一致 | 本文が一致（取得時の表現の差は除く）。Drive 外の形式はサイズも一致 | 正本を 1 件残し、他はゴミ箱へ（承認後） |
| 2. ほぼ同一 | 誤字・空白・書式程度の差。本文が同じでサイズが違う PDF・Office もここ（書き出しの関係なら 4） | 差分を示し、残す方はユーザーが決める |
| 3. 別バージョン | 同じ文書の編集段階違い（追記・削除・改稿） | 最新を正とする。旧版は既存のアーカイブ用フォルダへの移動、なければ `_v01` などへの改名だけを提案する。ゴミ箱は提案しない（旧版が新版に完全に含まれると本文で確かめたときだけ、§4-4 の確認のうえで選択肢として示してよい） |
| 4. 原本と派生 | 要約・抜粋・翻訳・書き出し・圧縮版など | 両方残し、関係を整理案とログに書く |
| 5. 関連するが別物 | 同じテーマで目的が違う | 両方残す。必要なら名前で役割を区別する |
| 6. 判断不能 | 根拠が足りない、または矛盾する | 要確認 |

### 4-2. 比較と根拠

- 比べる観点: 見出し構成、主要な文章、表やデータ、追記・削除の位置、Frontmatter、ファイル間の参照、作成目的。
- 差分は、見出しの対応と、差のある一節の短い引用で示す。誤字程度の差は、取得時の表現の差と区別できなければ断定しない。
- 途中で切れていそうな読み取り（終わり方が不自然、サイズに比べて極端に短い）は、一致・不一致の根拠にしない。

### 4-3. 最新版と分岐

- 名前（「最終版2」「最新版」など）ではなく、内容で判断する。名前は付けた時点の意図にすぎない。
- 一方が他方の内容をすべて含み、さらに追記があるなら、追記がある方を新しいとみなす。包含は記述の有無（事実・場面・項目）で見る。同じ内容の言い換えは改稿として扱い、どちらが新しいか決まらなければ要確認にする。
- 互いに相手にない内容がある、または包含の向きが更新日時の順と逆なら、**分岐**として要確認にする。統合するかはユーザーが決める。

### 4-4. 正本（残す 1 件）とゴミ箱側の確認

- 正本の優先順: ① 整理後の置き場所にある ② 他のファイルからリンクされている、または共有されている ③ 名前が整っている ④ 作成日時が古い。
- 確度「高」が決まったら、ゴミ箱側の 1 件だけ `get_file_permissions` で共有を確かめる。共有されていれば、そちらを正本にするか、ゴミ箱の案を取り下げる。
- ゴミ箱側が Vault 内のノートや添付なら、改名と同じリンク確認を行う（`references/obsidian.md` §6）。被リンクの可能性があれば、ゴミ箱の案にせず要確認にする。
- ゴミ箱候補と同名のショートカットがあれば、参照先の可能性があるので警告を付ける。
- バックアップ・アーカイブ用のフォルダの中の複製は、意図して置かれた可能性があるので要確認にする。
- ゴミ箱の案を出したファイルには、改名・移動・Frontmatter の案を出さない。

### 4-5. 本文を比較できないファイル

画像・動画・音声・圧縮ファイルは、メタデータが一致しても確度は「中」まで。要確認に `viewUrl` を付けて目視を依頼する。ユーザーが同一と確かめたうえで移動を指示すれば、その返答を承認として扱ってよい。

### 4-6. 統合

2 つの文書の本文を 1 つにまとめるのは本文の編集なので、実行しない。どちらに何を移すかという統合案を示すまでとする。

## 5. Obsidian

Obsidian 対象の Markdown について案を作る、または実行するときは、先に `references/obsidian.md` を読む。読まないまま、Vault 内のファイルの改名・移動・ゴミ箱・Frontmatter の案を出さない。要点は次のとおり。

- **対象**: Vault ルート配下の Markdown、またはユーザーが指定したもの。日記ノート、テンプレート、`.excalidraw.md`、自動命名の添付ファイルは改名しない。判断できなければ保留する。
- **命名**: 改名は、検索性・識別性・管理性が実際に上がるときだけ。Vault の規約（多数派のパターン）に合わせ、時間で意味が変わる語を避け、日付は `YYYY-MM-DD` にする。Vault 内でファイル名が一意であることを優先する。
- **Frontmatter**: 既存の意味のあるキーを消さない。キー名と書式は規約に従う。title はファイル名と違う必要があるときだけ、date は本文か名前に明記された日付だけ、type は既存の語彙に従う。
- **aliases**: 実際に使われる別名だけ（0〜3 個）。旧名を入れても、既存の `[[旧名]]` リンクは直らない。
- **tags**: 既存の語彙を優先し、1 ノート 1〜3 個。本文の単語を機械的にタグにしない。
- **リンク**: 被リンクがある、または確かめきれないノートの改名は、方法を「Obsidian で改名」にする。確認の状態（確認済み／検索ベース／未確認）を必ず書く。

## 6. 承認と実行

### 6-1. 承認の要否

| 操作 | 扱い |
|---|---|
| 検索・読み取り | 承認不要 |
| ログ・整理案ファイルの保存（ログ用フォルダとその中） | 定期実行では承認不要（初回に置き場所を伝える）。対話では保存を申し出て、了承を得てから |
| フォルダ作成・移動・改名、Frontmatter のローカル適用 | 整理案への承認で実行する（具体的な指示は、その指示が承認） |
| 20 件を超える改名・移動、命名規則・タグ体系・キー名の一括変更 | 整理案に件数と例を示したうえで承認を得る |
| ゴミ箱への移動 | ID を挙げた明示的な承認が必要。「全部」「おまかせ」には含めない |
| 完全削除、本文の書き換え、他人がオーナーのファイルの変更、共有設定の変更 | 行わない |

範囲の曖昧な承認（「いい感じにやって」）では実行せず、実行する ID の一覧を示して確かめる。「全部」と返信されたら D 以外を実行し、D は ID を挙げてあらためて確認する。

### 6-2. 実行手順

1. **事前確認**: 対象のフォルダの子を OR でまとめて取り直し、各対象（重複の正本側も含む）のタイトル・親・更新日時が整理案と一致するかを確かめる。ID の取り違えも、ここで見つける。整理案に更新日時がない項目は、整理案の日付より後に更新されていないことを確かめる。整理案にファイル ID がないとき（ユーザーが貼った整理案など）は、パスと名前が取り直した結果と 1 対 1 で対応すれば特定できたとみなし、曖昧なら尋ねる。正本が更新されていれば「完全一致」の前提が崩れているので、その D は保留する。
2. **衝突確認**: 同じ結果で、移動先や新しい名前に同名のファイルがないかを確かめる。Vault 内の改名では、インベントリ（正規化後）で Vault 全体の名前の一意性も確かめる。
3. **順序**: フォルダ作成 → 移動 → 改名 → ゴミ箱への移動。消す操作を最後にし、途中で止まっても何も失われないようにする。例外: 正本の新しい名前がゴミ箱側と同名になるときは、ゴミ箱へ移した後に改名する（衝突確認ではゴミ箱側の ID を除く）。この改名は D と一組にし、D が承認されなければ実行しない。
4. **ゴミ箱の挙動の確認**: ゴミ箱内のファイルが検索結果に出るかは未確認。最初のゴミ箱移動の直後に、同じ `title` と `parentId` で 1 回だけ検索する。まだ出るなら、正本がゴミ箱に入っていないことを Drive の画面で確かめるよう依頼し、ログに記録する。
5. **試行と停止**: 件数が多いときは、最初の 2〜3 件の結果を確かめてから進める。各操作の戻り値で結果を確かめ、失敗は 1 回だけ再試行し、続けて失敗したら止めて報告する。
6. **保留した項目**: 何が変わったかを示し、実行するなら、あらためて ID で承認を取る。前提が変わったことを理解したうえでのユーザーの指示なら、分類が変わった D（別バージョンになった、など）でも実行してよい。
7. **記録**: ID と変更前後をすべて記録し、元に戻す方法を示す。

## 7. 確度と優先度

### 7-1. 確度

| 確度 | 条件 |
|---|---|
| 高 | 本文を比較した、または明示的な根拠がある |
| 中 | メタデータが強く一致し、内容の一部（先頭など）も一致した。本文を比較できないファイルのメタデータ一致もここまで |
| 低 | 名前やサイズが似ているだけ |
| 要確認 | 作成目的など Claude が知りえない情報に依存する、または根拠が矛盾する |

ゴミ箱への移動を提案できるのは「高」だけ。改名・移動は「中」以上。「低」は候補として挙げるだけにする。

### 7-2. 優先度

1. 明確な重複、誤分類、重大な命名の問題
2. Obsidian での検索性を大きく改善できる問題
3. Frontmatter の不足で管理性が大きく損なわれている問題
4. 軽微な表記ゆれ（依頼されたとき、または他の変更のついでに無理なくできるときだけ）

好みだけを理由にした変更は提案しない。

## 8. 出力と作業ログ

- 整理案と作業ログは `references/templates.md` の形式で出す。同じ種類の要確認はまとめ、既定を「そのまま残す」とする。
- 作業ログは、提案だけで終えた回にも残す（範囲、件数、未解決の要確認、実行しなかった変更と理由を次回へ引き継ぐため）。対話では返答に書き、保存を申し出る。定期実行では必ず保存する。
- 保存先はログ用フォルダ（既定はマイドライブ直下の `_drive-organizer-logs`）。`.md` のまま（`disableConversionToGoogleType: true`）、毎回新しいファイル `YYYY-MM-DD_HHmm_drive-organizer.md` として作る（コネクタでは上書きできない）。Vault の中には置かない。
- 保存する整理案と承認待ちの項目には、ファイル ID と操作の詳細（移動先、新しい名前、正本）を書く。後日の承認・却下の結果も、新しいログとして 1 件書く。

---

## 9. 定期実行と、前回の続き

`references/scheduled.md` に従う。前回の状態が取得できなければそう明記し、存在しない履歴を推測しない。定期実行では、事前承認があっても、ゴミ箱への移動、Vault 内のファイルの改名・移動、Frontmatter の適用はしない。
