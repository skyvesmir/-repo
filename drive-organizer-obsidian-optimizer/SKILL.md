# Drive Organizer & Obsidian Optimizer

Google Drive の大量ファイルを「メタデータ → 候補 → 必要な本文だけ」の順に調べ、承認された変更だけを実行する。Obsidian 用の Markdown は、既存 Vault の規約に合わせてファイル名と Frontmatter を整える。

このSkillの品質は次の3点で決まる。

1. **読む量を絞る**: 全ファイルの本文は読まない。同じファイルを二度読まない。
2. **断定しない**: 名前が似ていることは重複の証拠ではない。確かめていないリンクを「安全」と言わない。
3. **勝手に壊さない**: 破壊的な変更は承認後に行う。削除ではなくゴミ箱へ移す。本文はコネクタで書き換えない。

## 0. 開始前チェック

### 0-1. 使えるツールを確かめる

ツール名の接頭辞は環境によって異なる。下表は Google Drive コネクタでの名前。存在しないツールを前提にしない。

| 能力 | ツール | ないとき |
|---|---|---|
| 検索・一覧 | `search_files`, `list_recent_files` | 必須。接続を依頼して終了 |
| メタデータ | `get_file_metadata` | 検索結果で代用 |
| 本文 | `read_file_content`（読み取り用の表現）, `download_file_content`（原文の base64） | 本文比較なしで確度を下げる |
| 改名・移動 | `update_file`（`title` と `parentId` のみ変更可） | 提案のみ |
| ゴミ箱へ移動 | `trash_file`（完全削除のツールはない） | 提案のみ |
| 作成 | `create_file`（フォルダ、ログ） | ログは返答に書く |
| 共有の確認 | `get_file_permissions` | 共有の有無は要確認とする |

- **コネクタでは本文を書き換えられない**。Frontmatter の適用方法は §5-8 に従う。
- Phase 1 の前に `references/drive-connector.md` を読む（pageSize の実測上限、クエリの癖、本文表現のエスケープなど、呼び出し回数と正確さに直結する事実をまとめてある）。
- ブラウザ操作で大量整理をしない。コネクタがなければ、ユーザーが用意した一覧を材料に提案だけ行う。

### 0-2. 実行形態を決める

- **対話**: 整理案を出し、承認された項目だけを実行する。
- **定期実行**（スケジュールタスクなど、その場にユーザーがいない）: §9 に従う。原則として提案のみ。
- ユーザーが対象と操作を具体的に指示した場合（「A を B フォルダへ移動して」）は、その指示を承認とみなす。ただしゴミ箱への移動は、対象一覧を示して確認を取ってから行う。

### 0-3. 範囲を決める

- 指定フォルダがあればその配下。「Drive 全体」ならマイドライブ（`parentId = 'root'`）から下る。
- 他人がオーナーのファイルとショートカットは変更しない（報告のみ）。
- 次のフォルダは中身を列挙せず「除外」と記録する。中の名前を変えるとアプリやビルドが壊れるうえ、件数だけが膨らむため。
  - アプリが管理するフォルダ: `.obsidian`, `.trash`, `.git`, `Google AI Studio`, `Colab Notebooks` など
  - コード関連: `node_modules`, `.venv`, `venv`, `__pycache__`, `dist`, `build`、および `package.json`・`pyproject.toml`・`.git` などを直下に持つフォルダ

## 1. 安全の不変条件

効率化を理由に、以下を省略しない。

1. 完全削除はしない。不要なものは承認後に**ゴミ箱へ移動**する。ゴミ箱からの復元は Drive の画面で行う（通常 30 日以内）とユーザーに伝える。コネクタには復元の手段がない。
2. 重複グループからは必ず 1 件以上を残す。同じ実行の中で、互いを消し合う操作を組まない。
3. 名前・サイズ・日時だけで重複と**確定**しない。確定には本文の比較が必要（§4）。
4. コネクタで本文を書き換えない。「新しく作成して旧ファイルをゴミ箱へ」という置き換えもしない。ファイル ID・版の履歴・共有設定が失われ、全文を書き写す過程で本文が変わるおそれがあるため。
5. 被リンクを確かめきれないノートについて「リンクは壊れない」と言わない。
6. 既存 Vault の規約（命名、キー名、タグ体系）を上書きしない。規約そのものを変える提案は、影響件数を示して別途承認を取る。
7. 実行の直前に、対象が整理案を作った時点から変わっていないことを確かめる。変わっていればその項目は実行しない。

## 2. ワークフロー

### Phase 1: 全体把握（メタデータのみ）

- フォルダを上から幅優先でたどる。1 回の検索で複数フォルダの子をまとめて取る（`parentId = 'A' or parentId = 'B' …`）。本文スニペットは除外する。詳細は §3。
- 結果から**インベントリ**（ID、タイトル、MIME、サイズ、作成・更新日時、親、オーナー）を作り、以後の判断はすべてこれを使う。
- `.obsidian` フォルダを直下に持つフォルダを **Vault ルート**として記録する。
- 除外フォルダ（§0-3）には入らない。

### Phase 2: 候補抽出（インベントリだけで）

| 記号 | 候補の種類 | 意味 |
|---|---|---|
| S | 同じ MIME・同じサイズ・同じ更新日時 | アップロードでは元の更新日時が保たれるため、同じ元ファイルのコピーである可能性が高い |
| N | 正規化した名前が同じで、フォルダが違う | 同名ファイル。重複とは限らない |
| V | コピー・版の印がある名前（「(1)」「のコピー」「Copy of」「copy」「最終版」「最終版2」「最新版」「改訂版」「final」「new」「v2」など） | 印を除いた基本名が同じファイルとまとめる |
| Z | 同じ MIME・同じサイズ（1KB 以上）で名前が違う | 名前違いの同一ファイルの可能性 |
| L | 命名の問題（無題、前後や拡張子前の空白、Obsidian で使えない文字、Notion 書き出しの 32 桁 ID、極端に長い名前） | 改名候補 |
| O | Obsidian 対象と思われる Markdown | §5 |
| U | ユーザーが重複を疑っていると指定したファイル | 最優先。必ず本文を比較する |
| X | 分類できない・異常（拡張子と MIME の不一致、ほぼ空、など） | 要確認 |

- 名前の比較は、Unicode 正規化（NFKC）、大文字小文字の無視、前後の空白の除去をしてから行う。Mac 由来の日本語名は見た目が同じでも内部表現が異なることがある。
- 「(1)」などの記号は検索クエリでは拾えない。印の判定は取得済みのインベントリに対して行う。
- Google ドキュメントなどのネイティブ形式のサイズは本文量と対応しないことがあるため、S と Z の根拠にしない。
- ファイルシステムとコード実行が使える環境では、インベントリを TSV に書き出し、`scripts/find_candidates.py` で S・N・V・Z・L を機械的に抽出する（数百件を超えると目視より確実）。出力は候補であり、判定ではない。

### Phase 3: 詳細確認（必要なものだけ）

安い方法から順に使い、判断がつけばそこで止める（§3-3）。

1. 取得済みのメタデータ
2. 先頭部分: `snippetVerbosity: 'BRIEF'` の検索で、複数ファイルの先頭（約 1000 文字）を 1 回で取る。Frontmatter はたいていここに収まる。
3. 特徴的な一節での全文検索（`fullText contains '…'`）: その一節を含むファイルが 1 回でわかる。派生や転記の発見に使う。
4. 本文全体（`read_file_content`）: ゴミ箱への移動、統合、原本の特定など、判断がこれに依存するときだけ。

読んだファイルには要約メモを残す（見出し構成、Frontmatter、主な差分、外向きのリンク）。二度目は読まずにメモを使う。

### Phase 4: 分析

- 重複の分類と正本の選定: §4
- Obsidian のファイル名・Frontmatter・リンク: §5
- 移動先: 既存のフォルダ構成を優先する。新しいフォルダは、同じ分類のファイルが複数（目安 3 件以上）あり、置き場所がないときだけ作る。階層を深くしない。

### Phase 5: 整理案

`references/templates.md` を読み、その形式で出す。各項目に ID（D=重複、R=改名、F=Frontmatter、M=移動、Q=要確認）を付け、§7 の優先度順に並べる。最後に承認の方法（「全部」「D1, R2〜R5」「F 以外」など）を示す。変更が不要なら、不要と伝えて終える。

### Phase 6: 実行

承認された項目だけを §6 の手順で実行し、作業ログを残す（§8）。

## 3. 大規模処理の効率化

### 3-1. 呼び出しを減らす

- 一覧取得は `excludeContentSnippets: true` と pageSize 30 で行う。既定のスニペットは長く（約 5000 文字）、1000 件なら数百万文字になるため。
- 複数フォルダの子を OR でまとめて取る（1 回あたり 10〜20 フォルダ）。フォルダと中のファイルを同じ呼び出しで取れば、フォルダ一覧を別に取る必要はない。
- 検索結果にはメタデータが揃っている。同じファイルに `get_file_metadata` を重ねて呼ばない。
- 特定の複数ファイルを調べるときも 1 件ずつ呼ばず、`title = 'a' or title = 'b'` のようにまとめる。

### 3-2. コンテキストを守る

- メタデータは 1 件あたり約 500 文字、BRIEF スニペットは約 1000 文字。着手前に範囲の件数から量を見積もる。
- ファイルシステムが使える環境では、インベントリと要約メモをファイルに書き、会話の中で持ち回らない。
- チャットだけの環境で数百件を大きく超える場合は、フォルダ単位で区切って進め、各回の結果を作業ログ（§8）で引き継ぐ。一度に全部を抱えない。

### 3-3. 本文の読み取りを絞る

- 本文を読むのは候補だけ。U（ユーザー指定）、S、V、Z、N の順に優先する。
- 1 回の実行で本文を読むのは合計 30 件程度までを目安とする。超えそうなら、残りを要確認として一覧にし、続けるかどうかをユーザーに尋ねる。
- 大きなファイル（目安: 本文 10 万字超）は全文を読まず、先頭と特徴的な一節の検索で判断し、確度を下げる。サブエージェントが使える環境では、比較を任せて結論と根拠だけを受け取る。
- 画像・動画・音声・圧縮ファイルは本文を比較できない。メタデータが一致しても確度は「中」までとする。
- `read_file_content` の結果は Markdown 記号がエスケープされた表現になる（`\#`, `\-`, `\[`, `\---` など）。比較は同じ取得方法どうしで行い、この表現をファイルの原文として扱わない。

## 4. 重複判定

### 4-1. 分類

| 分類 | 基準 | 既定の推奨アクション |
|---|---|---|
| 1. 完全一致 | 本文が一致（取得時の表現の差は除く） | 正本を 1 件残し、他はゴミ箱へ（承認後） |
| 2. ほぼ同一 | 誤字・空白・書式程度の差 | 差分を示し、残す方はユーザーが決める |
| 3. 別バージョン | 同じ文書の編集段階違い（追記・削除・改稿） | 最新を正とし、旧版は `_v01` などへの改名かアーカイブへの移動を提案。ゴミ箱は提案しない |
| 4. 原本と派生 | 要約・抜粋・翻訳・書き出し・圧縮版など | 両方残し、関係を明記する |
| 5. 関連するが別物 | 同じテーマで目的が違う | 両方残す。必要なら名前で役割を区別する |
| 6. 判断不能 | 根拠が足りない、または矛盾する | 要確認 |

比較する観点: タイトル、見出し構成、本文の主要な文章、表やデータ、追記・削除の位置、作成目的、Frontmatter、ファイル間の参照。

### 4-2. 最新版の判定

- 「最終版2」「最新版」などの名前ではなく内容で判断する。名前は付けた時点の意図であり、その後の編集を反映しない。
- 一方が他方の内容をすべて含み、追記があるなら、追記がある方が新しい。
- 互いに相手にない内容を持つなら**分岐**として要確認にする。統合するかどうかはユーザーが決める。
- 更新日時は補助的な手がかりにとどめる。

### 4-3. 残す 1 件（正本）の選び方

優先順: ① 整理後の置き場所にある ② 他のファイルからリンクされている、または共有されている ③ 名前が整っている ④ 作成日時が古い。共有されているファイルをゴミ箱へ移す案は出さない（共有の有無は `get_file_permissions` で確かめる）。

### 4-4. 統合

2 つの文書の本文を 1 つにまとめる作業は本文の編集にあたるため、実行しない。どちらに何を移すかという統合案を示すところまでとする。

## 5. Obsidian 最適化

### 5-1. 対象判定

- **対象**: Vault ルート（`.obsidian` あり）配下の Markdown、またはユーザーが Obsidian 用と指定したもの。
- **確度中**: `[[リンク]]` や Frontmatter を持つ Markdown が集まったフォルダ。Vault ルートをユーザーに確かめてから変更案を出す。
- **対象外**: コードの README・CHANGELOG など、Vault 外の Markdown（ユーザー指定がなければ）。
- **Vault 内でも改名しない**: 日記ノート（Daily notes などのプラグインが日付形式のファイル名に依存する）、テンプレート（`<% %>` や `{{ }}` を含む Frontmatter は書き換えない）、`.excalidraw.md` などの特殊な拡張子、`Pasted image …` などの自動命名の添付ファイル（ユーザーが望む場合を除く）。
- 判断できないものは保留にする。

### 5-2. Vault の規約を先に把握する

変更案を作る前に、ノートの種類（フォルダ）ごとに 10 件程度の先頭部分を BRIEF スニペットで取り（1 フォルダ 1 回の検索）、次を集計する。

- ファイル名のパターン、Frontmatter のキー名と書式（リスト形式、日付形式）、タグの語彙と階層（`作品/六炎` など）、`type` の値

意図して整えられていると見えるノートの多数派を**規約**とし、「規約メモ」として残して以後の判断に使う。規約がない場合は、変更するファイルにだけ最小限の形を提案し、Vault 全体に一斉適用しない。

### 5-3. ファイル名

目的は、検索しやすく、`[[リンク]]` を作りやすく、名前から内容がわかり、長く運用しても崩れないこと。**改名は、検索性・識別性・管理性が実際に上がる場合に限る。** 既に適切な名前は変えない。

- 内容や役割がわかる名前にする。
- 「新規」「最新版」「最終版」「最終版2」「new」「copy」など、時間が経つと意味が変わる語は使わない。版を並存させる必要があるときだけ `v01`, `v02`, `v1.1` のように付ける。
- 日付を含めるときは `YYYY-MM-DD` にする。
- 同じ種類のファイルは同じパターンにそろえる（§5-6）。
- 長すぎる名前にしない（目安 40 文字以内）。曖昧な略語を作らない。日本語を無理に英語にしない。
- 使わない文字: `\ / : * ? " < > |`（OS で問題になる）、`# ^ [ ] |`（Obsidian のリンクが壊れる）、先頭の `.`、末尾の空白やピリオド、拡張子の直前の空白。
- フォルダ名と同じ情報を繰り返さない。ただし `[[名前]]` はファイル名で解決されるため、**Vault 内でファイル名が一意であること**を優先する。重複語を削ると同名ノートが生じる場合は削らない。
- Drive 上の Markdown の `title` には拡張子 `.md` を含める。

### 5-4. Frontmatter

Frontmatter の追加や変更は、管理性が実際に上がるときだけ提案する。既存の意味のあるキー（プラグイン用のキーを含む）は削除しない。キー名と書式は Vault の規約に従う。

- **title**: Obsidian は本体機能ではファイル名を表示名として使う。Vault が既に `title` を使っている場合、表示名にファイル名で使えない文字（`:` や `?` など）が必要な場合、公開用ツールなどで必要な場合に限って付ける。付けるならファイル名と整合させる。
- **aliases**: 実際に検索や入力に使われる別名だけにする（旧名のうち意味のあるもの、本文中で使われている略称・通称、英語と日本語の表記、読み、旧称）。ファイル名そのもの、「最終版2」「無題」、ID 付きの旧名は入れない。目安は 0〜3 個。**aliases に旧名を入れても、既存の `[[旧名]]` リンクは解決されない**（検索と入力補完の助けにとどまる）。
- **tags**: Vault の既存タグを最優先で使う。新しいタグは、複数のノートに当てはまり、既存の同義タグがない場合だけ提案する。1 ノートあたり 1〜3 個が目安で、多くても 5 個程度。本文の単語を機械的にタグにしない。フォルダや `type` と同じ情報をタグで繰り返さない（Vault がそうしている場合を除く）。
- **date**: 意味のある日付（会議日、執筆日、出来事の日付など、本文か名前に明記されたもの）だけを設定する。ファイルの作成日時や更新日時を流用しない。
- **type**: Vault の既存の語彙に従う。語彙がない場合は、種類で絞り込みたいという要望があるときだけ、`character`, `setting`, `chapter`, `research`, `reference`, `meeting`, `note` のような小さな固定語彙を提案する。
- YAML の書き方: `: # [ ] { } , &` などを含む値は引用符で囲む。プロパティ内の `[[リンク]]` は `"[[ノート]]"` と引用する。tags に `#` を付けない（タグに空白は使えない）。
- 単数形の `tag` / `alias` / `cssclass` は旧形式で、現行の Obsidian では `tags` / `aliases` / `cssclasses` が標準。移行は Vault 全体の規約変更として、件数を示して別途提案する。

### 5-5. filename / title / aliases の役割分担

- **ファイル名**: 安定した識別子。検索とリンクに使う。
- **title**: 人間が読む正式名称。ファイル名と違う必要があるときだけ持つ。
- **aliases**: 別名・旧名・検索の補助。

分けることで二重管理が生じるなら、無理に分けない。

### 5-6. 同じ種類のノートの一貫性

- 種類（フォルダ、`type`、タグ）ごとにノートをまとめ、命名・キー・タグを比べる。
- **同じ役割なら統一し、役割が違うなら維持する。** 役割は名前ではなく内容（先頭部分）で判断する。
- 例: 「シューニャ」「Shunya」「シューニャ設定」「キャラ_シューニャ」「主人公シューニャ」があれば、まず各ノートの役割を確かめる。同じ人物ノートの重複なら §4 で扱い、人物ノートと能力設定のように役割が違うなら両方残し、名前で役割がわかるようにする。

### 5-7. リンクの安全性

- Obsidian は `[[名前]]` をファイル名で解決する。**Obsidian の外（Drive 側）で改名すると、リンクは自動では書き換わらない。** 被リンクのあるノートや埋め込まれた添付ファイルを Drive 側で改名すると、リンクが切れる。
- 改名候補ごとに `fullText contains '旧名（拡張子なし）' and mimeType = 'text/markdown'` で検索し、Vault 内のヒットは「被リンクの可能性あり」とみなす。ヒットしないことは「リンクがない」ことの証明にならない（検索の取りこぼしがありうる）。
- リンク確認の状態を必ず記す: **確認済み**（関係するノートを読んで確かめた）／**検索ベース**／**未確認**。
- 改名の方法:
  - 被リンクあり、または検索でヒットあり → **Obsidian 上で改名**してもらう（設定「内部リンクを自動更新」が有効であることを確認してもらう）。整理案では「方法: Obsidian で改名」とする。
  - 検索でヒットなし → 承認後に Drive で改名してよい。ただし「検索ベースの確認」であることを伝え、改名後に Obsidian でリンク切れがないか確かめるよう案内する。
- Vault 内の移動: 最短パス形式の `[[名前]]` は、名前が一意なら移動では切れない。パス付きのリンク（`[[フォルダ/名前]]`）や Markdown 形式のリンク（`[x](../名前.md)`）は切れる。サンプルで Vault のリンク形式を確かめてから提案する。Vault の外への移動は提案しない。
- 添付ファイル（PNG, JPG, SVG, PDF, 音声, 動画など）: ノートと同じく改名・移動で埋め込みが切れる。関係が明確で、埋め込み元のノートが特定できたときだけ、ノートと名前をそろえる案を出す（方法は Obsidian 上での改名）。添付ファイルの一括改名はしない。

### 5-8. Frontmatter とリンク書き換えの適用方法

コネクタは本文を変更できない。次のどちらかで適用する。

1. **パッチとして渡す**（既定）: ファイルごとに変更後の YAML を示し、ユーザーが Obsidian 上（プロパティ編集など）で適用する。
2. **ローカルで直接編集する**: Vault のローカルフォルダにファイルツールでアクセスできる環境（Cowork でフォルダを共有している場合、ユーザーのマシン上の Claude Code など）に限る。承認後、Frontmatter の部分だけを正確に編集し、本文が変わっていないことを確かめる。Drive への反映は同期クライアントに任せる。

改名に伴うリンクの書き換えも同じ扱いとする。

## 6. 承認と実行

### 6-1. 承認の要否

| 操作 | 扱い |
|---|---|
| 検索・読み取り | 承認不要 |
| このSkill自身のログ・整理案ファイルの新規作成（ログ用フォルダ内） | 承認不要。初回に置き場所を伝える |
| フォルダ作成・移動・改名、Frontmatter のローカル適用 | 整理案で承認を得る（ユーザーが具体的に指示したものは、指示が承認） |
| ゴミ箱への移動 | 毎回、対象一覧を示して明示的な承認を得る |
| 20 件を超える改名・移動、命名規則・タグ体系・キー名の一括変更 | 影響件数と例を示して明示的な承認を得る |
| 完全削除、コネクタでの本文書き換え、他人がオーナーのファイルの変更、共有設定の変更 | 行わない |

「いい感じにやって」のような範囲の曖昧な承認では実行せず、実行する ID の一覧を示して確かめる。

### 6-2. 実行手順

1. **事前確認**: 各対象の現在のタイトル・親・更新日時が整理案と一致するか確かめる（フォルダ単位の検索でまとめてよい）。ID の取り違えも、ここで検出する。重複の正本側も、存在と未変更を確かめる。正本が変わっていれば「完全一致」の前提が崩れているので、再比較するか保留にする。
2. **衝突確認**: 移動先や新しい名前に同名のファイルがないか確かめる（`title = '新しい名前' and parentId = '移動先'`）。同期先のローカル環境では同名ファイルが競合を起こす。
3. **順序**: フォルダ作成 → 移動 → 改名 → ゴミ箱への移動。消す操作を最後にし、途中で止まっても何も失われないようにする。
4. **試行**: 件数が多いときは、最初の 2〜3 件の結果を確かめてから残りを進める。
5. **確認と停止**: 各操作の戻り値で結果を確かめる。失敗は 1 回だけ再試行し、続けて失敗したら止めて報告する。
6. **記録**: ID と変更前後をすべて記録し、元に戻す方法を示せるようにする。

## 7. 確度と優先度

### 7-1. 確度

| 確度 | 条件 |
|---|---|
| 高 | 本文を比較した、または明示的な根拠がある |
| 中 | メタデータが強く一致し、内容の一部（先頭など）も一致した。バイナリのメタデータ一致もここまで |
| 低 | 名前やサイズが似ているだけ |
| 要確認 | 作成目的など Claude が知りえない情報に依存する、または根拠が矛盾する |

ゴミ箱への移動を提案できるのは「高」だけ。改名・移動は「中」以上。「低」は候補として挙げるだけにする。

### 7-2. 優先度

1. 明確な重複、誤分類、重大な命名の問題
2. Obsidian での検索性を大きく改善できる問題
3. Frontmatter の不足で管理性が大きく損なわれている問題
4. 軽微な表記ゆれ（依頼されたとき、または他の変更のついでに無理なくできるときだけ）

好みだけを理由にした変更は提案しない。

## 8. 出力と作業ログ

- 整理案と作業ログは `references/templates.md` の形式で出す。
- 作業ログは、実行した回だけでなく、提案だけで終えた回にも残す（調査範囲、件数、未解決の要確認、実行しなかった変更とその理由を次回に引き継ぐため）。
- 対話では返答にログを書き、Drive への保存（ログ用フォルダ）を申し出る。定期実行では必ず Drive に保存する（§9）。
- ログを Drive に保存するときは、`.md` のまま保存する（Google ドキュメントに変換しない）。Vault の中には置かない。

## 9. 定期実行

- **前回の状態**: ログ用フォルダ（ユーザー指定がなければ、マイドライブ直下の `_drive-organizer-logs`）で、名前が最も新しいログを読み、先頭の状態ブロックを使う。コネクタではファイルを上書きできないため、ログは毎回新しいファイル（`YYYY-MM-DD_HHmm_drive-organizer.md`）として作る。
- **前回の状態がない場合**: そう明記し、範囲を絞った通常の初回調査として扱う。存在しない履歴を推測しない。
- **差分の処理**: 次を優先する。
  1. `modifiedTime > '前回の last_scan'` または `createdTime > '前回の last_scan'` のファイル（範囲外は、既知のフォルダ ID で除く）
  2. 新しいファイルと同名・同じ基本名のファイル（`title = '…'` をまとめて検索）
  3. 前回の要確認項目と、承認待ちの提案（まだ存在するか、変わっていないかを確かめる）
  4. ユーザーが却下した提案は、状態ブロックの `declined` に従って繰り返さない。
- **実行の範囲**: 定期実行は原則として提案のみとし、整理案をログに書く。タスクの指示でユーザーが事前に承認した種類の操作だけ、確度「高」のものに限って実行してよい。ただし、事前承認があっても、ゴミ箱への移動、Vault 内の Markdown の改名、Frontmatter の適用は実行しない（見る人がいない状態で行うには取り消しにくいため）。
- **全体の再調査**: 差分だけでは見つからない重複（離れたフォルダにある同じサイズのファイルなど）があるため、状態ブロックの `last_full_scan` が古くなったら（目安 1 か月）全体の再調査を提案する。
